[课程主页列出的原版录像播放列表](https://www.youtube.com/playlist?list=PLoROMvodv4rMqXOcazWaTUHhq-yembLCV)可用于观看。

本讲要解决两个相互关联的问题：单卡算力和显存无法支撑更大模型时，怎样让多卡共同计算；并行之后，参数、优化器状态、梯度、激活究竟分布在哪些设备上，代价又落在哪条网络链路上。

可先记住每类并行**切的是什么**：

- **数据并行（DP, Data Parallelism）**：切样本
- **流水线并行（PP, Pipeline Parallelism）**：切层
- **张量并行（TP, Tensor Parallelism）**：切矩阵
- **序列并行（SP, Sequence Parallelism）／上下文并行（CP, Context Parallelism）**：切 token
- **专家并行（EP, Expert Parallelism）**：切专家

文中使用到的缩写：

- **MoE**：Mixture of Experts（混合专家）
- **MLP**：Multilayer Perceptron（多层感知机）
- **FSDP**：Fully Sharded Data Parallel（完全分片数据并行）
- **ZeRO**：Zero Redundancy Optimizer（零冗余优化器）

硬件与数值缩写：GPU 是 Graphics Processing Unit（图形处理器），TPU 是 Tensor Processing Unit（张量处理器），BF16 是 Brain Floating Point 16（16 位脑浮点格式）。下文 DDP 指 Distributed Data Parallel（分布式数据并行），Adam 指 Adaptive Moment Estimation（自适应矩估计优化器）。

## 1. 多机训练的前提：网络拓扑与集合通信（第 4–13 页）

**面试速述：** 多机扩展的有效收益由计算是否均衡以及 collective 穿过哪一级网络决定；增加总显存不等于每种并行方案都能容纳更大单模型。设计前应先画 rank 与拓扑，再按聚合后是否要全量结果选择通信原语。

### 从单卡扩展到数据中心

一块 GPU 的计算速度、显存容量都有上限。扩展到一个节点内的多 GPU，再到多个节点后，算力总量与可用显存理论上都可以增加；实际能否接近线性扩展，取决于通信量、链路带宽/延迟，以及工作是否均衡。这里的“总显存增加”不等于任何并行方式都能放下更大的单模型：朴素数据并行仍在每块 GPU 上保存一整份模型。

讲义先比较通信拓扑。TPU 传统上常用环面网格，GPU 集群可以在某个高速互联域内提供更灵活的全互连或交换网络。网格通常较省布线，并适合规则的邻近通信；树/交换式连接更适合目的地不规则的流量，例如 MoE 的 token 路由。讲义也指出 TPU8i/t 的网络设计正在变化，所以“TPU 必然网格、GPU 必然全互连”并不是普遍定律。互联域不能无限扩张：连接数、交换设备、布线、成本和跨域带宽都会成为限制。选并行方式时先画清楚**单节点、节点间、跨机架**哪些链路快。

**面试速述：** 从单卡扩展到数据中心，算力和总显存虽增加，慢链路、布线成本与负载偏斜会限制线性加速。节点内和跨节点带宽不同，拓扑也因设备设计而异，不能简单假定某类加速器总是固定网络形态。

### 五种基本 collective

设 $N$ 个 rank，每个 rank 有大小为 $S$ 的张量。先看讲义这张 rank 级图示，**读图重点是「每个 rank 最终拿到什么」**：

![五种 collective 的 rank 级图示：All reduce、Broadcast、Reduce、All Gather、Reduce Scatter](assets/lecture08-collective-communication.png)

图：讲义 collective 基础页（以 4 个 rank 为例）。逐项对照：

- **All reduce**：四个 rank **都**拿到聚合结果，`out[i] = sum(inX[i])`。
- **Broadcast**：只有 root（图中 rank 2）持有输入，复制给所有 rank，`out[i] = in[i]`。
- **Reduce**：只有 root 得到逐元素聚合结果，其余 rank 不保留。
- **All Gather**：每个 rank 各持一片，操作后**每个 rank 都拿到拼接完整的张量**。
- **Reduce Scatter**：先逐元素聚合，再把结果**切片分发**给各 rank，每人只留一片。

把 **All reduce ↔ Reduce**、**All Gather ↔ Reduce Scatter** 两两对照即可看出：`all` 前缀改变的是**结果的接收范围**（只给 root，还是人人都有）。

| 操作 | 每个 rank 最终拿到什么 | 本讲中的典型用途 |
| --- | --- | --- |
| Reduce | 仅目标 rank 拿到逐元素聚合结果 | 汇总梯度到指定设备 |
| All-reduce | 每个 rank 都拿到聚合结果 | 朴素 DP 的梯度同步；TP 的部分和 |
| All-gather | 每个 rank 拿到各 rank 分片拼接后的完整张量 | ZeRO 的参数恢复；序列分片转完整输入 |
| Broadcast | 源 rank 的张量复制给其他 rank | 同步同一份输入或参数 |
| Reduce-scatter | 逐元素聚合后，每个 rank 只保留结果的一片 | ZeRO 的分片梯度；TP/SP 的输出切片 |

以求和为例，all-reduce 可以拆为 **reduce-scatter + all-gather**：前半步让每个 rank 持有全局和的 $1/N$ 分片，后半步把所有分片交换给每个人。在理想环算法、带宽主导且每 rank 原始张量大小为 $S$ 字节时，两步各传约 $\frac{N-1}{N}S$ 字节/设备，总计 $2\frac{N-1}{N}S$。课程常把 $N$ 较大时的这一量简写为 **$2S$**；它是每设备通信量的近似，不是整个集群的总流量，也没有算启动延迟、拥塞和拓扑损耗。后面“$2P$ / $3P$”以 $P$ 个参数大小的张量为单位，乘上通信 dtype 的字节数才是字节流量。

![all-reduce 的两步分解：reduce-scatter 聚合后各留一片，再 all-gather 把分片拼回每人一份](assets/lecture08-allreduce-decomposition.png)

图：讲义「all reduce vs reduce-scatter + all-gather」一页（左右对照，4 个 GPU）。**上半图是输入，下半图是操作后的状态**：

- **左：All Reduce** —— 四张卡各持 `A`、`B`、`C`、`D`，一次操作后**每张卡都拿到 `A+B+C+D`**。
- **中：Reduce-Scatter（第一步）** —— 先逐元素聚合，再把结果**切片分发**：`rank0` 只留 `A0+B0+C0+D0`，`rank1` 只留 `A1+B1+C1+D1`，依此类推，每人一片。
- **右：All-Gather（第二步）** —— 把各卡手里的那一片**拼接**起来，于是**每张卡又都拿回了完整的 `A B C D`**。

把中、右两步合起来看，**结果与左边的 All Reduce 完全一致**——这就是 "all-reduce = reduce-scatter + all-gather" 的图示含义，也是后面 DDP、FSDP/ZeRO 通信量核算（$2P$、$3P$）反复用到的基础。

**面试速述：** collective 的关键是结果位置：all-reduce 给所有 rank 完整聚合结果，reduce-scatter 只保留聚合分片，all-gather 恢复完整张量。理想环形 all-reduce 可视为后两步组合，每设备通信约 $2(N-1)S/N$；这个量不含启动延迟与拓扑损耗。

## 2. 数据并行与 ZeRO：先处理模型状态（第 14–30 页）

**面试速述：** 朴素数据并行复制模型状态；ZeRO 逐级分片优化器状态、梯度和参数以节省常驻显存。前两级主要改变通信形式，三级还需聚齐参数、通常增加流量；评估峰值显存时也要计入临时参数和激活。

### 朴素数据并行的算力收益与显存瓶颈

对全局 batch 大小 $B$，$N$ 个数据并行 rank 各算约 $B/N$ 个样本的梯度，再同步并平均；若损失定义为样本均值，更新为

$$\theta_{t+1}=\theta_t-\eta\frac{1}{B}\sum_{i=1}^{B}\nabla_\theta f(x_i;\theta_t).$$

讲义第 15 页把梯度写作求和；上式的 $1/B$ 取决于损失与学习率约定。每个 rank 仍需完整参数。若模型有 $P$ 个参数，一次梯度 all-reduce 约传 $2P$ 个梯度元素；batch 越小，每卡计算越少，通信占比越高。DP 能扩大**总吞吐**和全局 batch，却不能单靠复制模型解决单卡装不下的问题。

按讲义的混合精度 Adam 记账，每参数有 BF16 参数 2 字节、BF16 梯度 2、FP32 主权重 4、一阶矩 4、二阶矩 4，合计 **16 字节/参数**，尚未计入激活、临时缓冲、CUDA/框架开销。所谓“五份状态”并不是五份同精度权重。如果两个 Adam 矩也用 BF16，则变成 12 字节/参数；具体精度与数值稳定性必须按实现选择。

**面试速述：** 朴素数据并行把 batch 分给各卡并同步平均梯度，提高吞吐，但每卡仍保存完整参数、梯度和 Adam 状态。讲义的混合精度示例是每参数 16 字节静态状态；真实显存还包括激活和缓冲，小 batch 也可能让通信占主导。

### ZeRO-1：仅切优化器状态

设每参数复制的“参数 + 梯度”占 $C$ 字节，优化器状态（含主权重）占 $K$ 字节，DP 规模为 $N$。朴素 DP 每 rank 需 $(C+K)P$；ZeRO-1 为 $(C+K/N)P$。采用上面的 16 字节例子，$C=4,K=12$。每个 rank 只负责更新自己那 $1/N$ 的参数：本地完整反向 → 梯度 reduce-scatter → 本地用自己的状态更新参数分片 → 参数 all-gather。通信仍约 $P+P=2P$，所以在带宽主导的简化模型中，节省优化器显存并未增加主导通信量；现实还受 collective 启动和额外缓冲影响。

讲义用一页「how it works」把这句话展开成四步，下面两张 rank 图分别对应第 2 步和第 4 步的通信：

![ZeRO-1 的四个步骤：本地完整反向 → 梯度 reduce-scatter → 本地更新 → 参数 all-gather](assets/lecture08-zero1-how-it-works.png)

图：讲义 ZeRO 第 1 级的流程页。逐步对照：

1. **Step 1**：每张卡在**自己那部分 batch** 上算出**完整梯度**——注意不是"只算自己那一片参数的梯度"，反向必须算全模型的。
2. **Step 2 · ReduceScatter**：把梯度按 rank 切片规约（`out[i] = sum(inX[*count+i])`），于是**每张卡只留下属于自己参数分片的那一段梯度**，其余发送出去后即可释放。**通信量 ≈ 一个 $P$**。
3. **Step 3**：每张卡用「自己那一段梯度 + 自己那一片优化器状态」更新**自己负责的那一片参数**，其余参数不归它管。
4. **Step 4 · AllGather**：把各卡更新好的参数分片**拼回完整参数**（图上四张卡的色块又都变满），供下一轮前向使用。**通信量 ≈ 一个 $P$**。

所以 ZeRO-1 每步通信 ≈ $P$（reduce-scatter）$+\,P$（all-gather）= **$2P$**，与朴素 DP 的梯度 all-reduce 同量级——**它省的是显存，不是通信**。图里第 4 步各卡又都拿回完整参数，正说明"完整参数仍须放得进单卡"这一限制。

**面试速述：** ZeRO-1 只分片优化器状态，每卡仍有完整参数与梯度；各卡更新所负责参数后再聚齐权重。它主要缓解 Adam 状态显存，简化带宽模型下通信主导量仍约为两个参数大小，完整参数仍须放进单卡。

### ZeRO-2：进一步切梯度

ZeRO-2 每 rank 保留完整参数，但梯度和优化器状态分片，静态模型状态近似为 $(C_{\rm param}+(C_{\rm grad}+K)/N)P$。难点在于每个 rank 对本地样本做反向时，仍必须**计算每层完整的局部梯度**；它只是不把全模型梯度一直留在显存里。做完一层就对这一层 reduce-scatter，把属于别人的部分发送并释放；最后本地更新，再 all-gather 参数。于是通信主导项仍约 $2P$，但梯度桶、重叠和释放时机决定峰值显存。

与 ZeRO-1 的关键差异在于**「边算边发、算完即释放」**，讲义用一页流程图说明：

![ZeRO-2 的流程：反向逐层规约并立即释放梯度，再更新分片参数并 all-gather](assets/lecture08-zero2-how-it-works.png)

图：讲义 ZeRO 第 2 级的流程页。逐步对照：

1. **Step 1**：不再等整个反向结束才同步，而是**沿着计算图逐层反向**。
2. **Step 1a**：每算完一层的梯度就**立刻规约并发送给对应的卡**。图中以「规约到 root」示意（`out[i] = sum(inX[j])`）；真实实现是 **reduce-scatter**——规约的同时把结果切片分给各卡，即 §1 那张分解图右侧的两步。这一步是 ZeRO-2 相对 ZeRO-1 额外付出的通信。
3. **Step 1b**：这一层的梯度一旦在反向图中不再需要，就**立即释放**——这是它降低峰值显存的来源。
4. **Step 2**：每张卡用「自己那段梯度 + 自己那片优化器状态」更新**自己负责的那片参数**。
5. **Step 3 · AllGather**：把参数分片拼回完整参数（图下排四张卡的色块又都变满）。

所以 ZeRO-2 的通信仍约 $2P$（逐层 reduce-scatter 累计约 $P$，最后 all-gather 约 $P$）：**它多切的是梯度显存，而不是增加通信量**。

**面试速述：** ZeRO-2 进一步用 reduce-scatter 分片并及时释放梯度，常驻显存降低，但反向仍要计算各层完整的本地梯度。通信主导量与 ZeRO-1 近似，实际峰值取决于梯度桶和释放时机，参数仍是完整复制的。

### ZeRO-3 / FSDP：参数也切开

每 rank 常驻参数、梯度、优化器状态的 $1/N$ 分片，理论静态模型状态接近 $(C+K)P/N$。执行某个 FSDP 单元的前向时 all-gather 该单元参数，算完释放完整临时副本；反向前再 all-gather 参数，算完把梯度 reduce-scatter 到所属 rank，随后释放临时副本并本地更新。按讲义“朴素版本”，每步约 **两次参数 all-gather + 一次梯度 reduce-scatter = $3P$**；相比 DP/ZeRO-1/2 的 $2P$ 是约 1.5 倍通信量。精确环算法因子是 $(N-1)/N$；峰值显存还要加当前/预取单元的完整参数、激活与通信缓冲，不能直接等同于静态状态除以 $N$。

讲义用一页"baby version"时序图把这段流程画了出来（上下两行各是一条流水线）：

![ZeRO-3 / FSDP 执行时序：LOAD SHARD → ALL-GATHER → FORWARD → FREE → ALL-GATHER → BACKWARD → REDUCE-SCATTER → FREE → UPDATE](assets/lecture08-zero3-how-it-works.png)

图：讲义 ZeRO-3（aka FSDP）的执行时序页。沿时间轴读一遍：

1. **LOAD MODEL SHARD**：每张卡只把自己那一片参数读进来（开启 CPU offload 时从 CPU 加载）。
2. **ALL-GATHER**：把**当前这个 FSDP 单元**的完整参数聚齐，形成临时副本。
3. **FORWARD (LOCAL)**：用完整参数做本单元前向。
4. **FREE FULL WEIGHTS**：算完**立即释放**完整参数副本，只留自己那一片。
5. **ALL-GATHER（第二次）**：反向前**再聚齐一次**该单元参数（所以前向、反向各一次）。
6. **BACKWARD (LOCAL) → REDUCE-SCATTER**：算完梯度就规约切片，各卡只留下自己负责的那部分。
7. **FREE FULL WEIGHTS**：再次释放完整参数。
8. **UPDATE WEIGHTS (LOCAL)**：各卡用自己那片梯度与状态更新自己那片参数；然后进入下一个 FSDP 单元，循环重复。

页末给出的通信账与正文一致：**2× all-gather + reduce-scatter（以参数个数计）**，讲义特意注明 “so we have one extra all-gather”——因为参数在**前向和反向各聚一次**，比 ZeRO-1/2 那类"只聚一次参数"的方案多出一次 all-gather，这正是 $2P \to 3P$ 的来源。

顺带两点读图提示：图左侧的 **CPU offload** 只出现在 LOAD SHARD（从 CPU 加载分片）与 FREE（把梯度卸回 CPU）两处，**不影响上面这笔通信账**；图中 "FSDP instance 1 … FSDP instance N" 表示同一套流程会**逐个单元**重复，这也就是正文所说的"逐单元"粒度。

讲义把这一级总结为「shard everything」：

![ZeRO-3 / FSDP：连参数也分片，沿计算图按需索取参数](assets/lecture08-zero3-shard-everything.png)

图：讲义 ZeRO 第 3 级（aka FSDP）一页（右侧公式与后面总览图的最后一行是同一组数据）。$\dfrac{(2+2+K)\Psi}{N_d}$ 对应 **1.9 GB**——**连参数一起切**之后，每卡静态状态降到约 $1/N$。页面上三条要点：

- **Shard everything**：参数、梯度、优化器状态**全部**分片，这是与前两级唯一的结构差别（前两级参数始终完整复制）。
- **沿用同一套「增量通信 / 增量计算」思路**：即 ZeRO-2 那种"边算边发、算完即释放"，只是这次释放的是**参数**而非梯度。
- **沿计算图按需发送与索取参数（on demand）**：这就是上文"前向 all-gather 该层参数、用完释放"的来源——谁走到哪一层，才在那一步把该层参数聚起来。

页末讲义自己提了一个问题：**“Is it possible to do this with low overhead?”**——按需索取意味着通信次数显著增多，所以紧接着就讲下面的「逐单元通信与计算重叠」。

讲义第 26 页强调逐单元通信和计算重叠：例如前向算当前单元时预取下一个单元参数、反向边算边规约。异步调度能隐藏部分传输时间，但受网络、单元粒度及依赖顺序限制。

讲义用一页"实际调度"图把重叠画成了三条并行的时间线（原图出自 [FSDP 论文](https://arxiv.org/pdf/2304.11277.pdf)）：

![FSDP 的通信/计算重叠时间线：All-Gather 与前向并行、Reduce-Scatter 与反向并行，参数用完即释放](assets/lecture08-zero3-overlap-schedule.png)

图：讲义「Actual picture of how FDSP / ZeRO stage 3 works」一页。图例：**AG** = All-Gather、**RS** = Reduce-Scatter、**FWD / BWD** = 前向 / 反向计算、黄色小块 = **Parameter Free**（参数释放）、`i` = 第 $i$ 个 FSDP 单元。

- **CPU 行**：`0 0 1 1 0 2 2 2 2 0 1 1 0 0`，数字是**FSDP 单元编号**——调度器在此起彼伏地摆布单元，**不是"先做完整个前向再做反向"**，而是逐单元交错。
- **GPU Comp. Stream**：`FWD0 FWD1 FWD1 FWD0 FWD2 FWD2 BWD2 BWD2 BWD0 BWD1 BWD1 BWD0` 交错执行，色块为前向（浅蓝）与反向（浅绿）计算。
- **GPU Comm. Stream**：`AG0 AG1 RS1 RS0 …` 与上面**并行推进**，色块为 All-Gather / Reduce-Scatter。

页面上两句结论正对应这一段正文：

- **Incremental computation / communication** —— 参数与梯度**随取随用、用完立即释放**；
- **Overlapping communication and computation** —— 以 $(W_1W_0+W_2W_0)x=y$ 为例，**all-gather 在计算进行的同时被一次接一次地发起**，把通信开销**掩盖在计算里**。

所以"重叠"并不减少通信量，而是**让通信与计算共用同一段时间**——这也是上面那笔 $3P$ 通信账在真实实现里没有纸面上那么痛的原因。但重叠程度受网络带宽、单元粒度与依赖顺序限制，不能假定一定被完全掩盖。

ZeRO-3 解决参数状态问题，**没有自动消除激活显存**。ZeRO-1/2 的完整参数仍必须放得进单卡；当全局 batch 太小，DP rank 数还会受样本数与梯度同步开销制约。

**面试速述：** ZeRO-3/FSDP 连参数也分片，计算某层时临时 all-gather，反向再聚齐参数并 reduce-scatter 梯度，因此能突破单卡完整参数的容量限制。讲义朴素模型每步约 $3P$ 通信，高于前两级的约 $2P$；静态状态的 $1/N$ 不代表实际峰值显存。

讲义用一页图把四个阶段并排对照。**核心思路一句话：把昂贵的那部分（优化器状态、梯度、参数）切开，并复用 reduce-scatter 的等价性。**

![ZeRO 各阶段显存总览：Baseline、P_os、P_os+g、P_os+g+p 的通用公式与一组具体数值](assets/lecture08-zero-stages-memory.png)

图：讲义的 ZeRO 总览页。色块含义：蓝 = Parameters（参数）、橙 = Gradients（梯度）、绿 = Optimizer States（优化器状态）。右侧给出通用公式与一组具体数值（$K=12$ 为优化器状态字节数、$\Psi$ 为参数量、$N_d$ 为卡数）：

| 阶段 | 每卡静态状态 | 讲义数值（$\Psi=7.5$B，$N_d=64$） |
| --- | --- | ---: |
| Baseline（朴素 DP） | $(2+2+K)\Psi$ | 120 GB |
| $P_{os}$（ZeRO-1，切优化器状态） | $2\Psi+2\Psi+\dfrac{K\Psi}{N_d}$ | 31.4 GB |
| $P_{os+g}$（ZeRO-2，再切梯度） | $2\Psi+\dfrac{(2+K)\Psi}{N_d}$ | 16.6 GB |
| $P_{os+g+p}$（ZeRO-3 / FSDP，参数也切） | $\dfrac{(2+2+K)\Psi}{N_d}$ | 1.9 GB |

读图看两条线索：

- **公式里分母有没有 $N_d$** —— 分母出现 $N_d$ 的那一项就是被分片的那一项（优化器状态 / 梯度 / 参数），逐级多切一样东西。

### 8×A100 80 GB 的课堂估算

讲义第 28 页换用 12 字节/参数的假设：BF16 参数 2、BF16 梯度 2、FP32 主权重 4、BF16 两个 Adam 矩各 2。令 $N=8$，单卡暂按十进制 80 GB、忽略所有激活和缓冲，则：

| 策略 | 每参数每卡字节数 | 理论最大参数量 |
| --- | ---: | ---: |
| 朴素 DP | $12$ | $80/12\approx6.67$B |
| ZeRO-1 | $2+2+8/8=5$ | $16$B |
| ZeRO-2 | $2+(2+8)/8=3.25$ | $\approx24.62$B |
| ZeRO-3 | $12/8=1.5$ | $\approx53.33$B |

这里 B 指十亿参数，不是 batch。上述是**仅模型状态的乐观上界**：真实可训练模型必须为激活、临时 all-gather、通信桶、内核工作区及运行时预留空间。讲义第 28 页先说“纯 BF16 训练配合 Kahan 求和可以可行”；Kahan 是用补偿量减少浮点累加误差的方法。随后讲义用“除 FP32 主权重外其余 BF16”的 12 字节口径做表；前者是低精度累加的数值条件，**不等于**表中的主权重已被删除。不能把该口径与前面 FP32 Adam 矩的 16 字节直接混用。

**面试速述：** 8×80 GB 示例按 BF16 Adam 矩的 12 字节/参数记账，ZeRO 级别越高，每卡静态模型状态越少，理论可容纳的参数量越大。表中的最大参数量忽略了激活、临时参数副本和运行时开销，也不能与前面 FP32 Adam 矩的 16 字节口径混用。

## 3. 模型并行：先切深度，再切宽度（第 31–43 页）

数据并行让每卡处理不同样本；模型并行则让不同卡持有模型的不同部分，主要传**激活或部分结果**。因此可以在不扩大 batch 的情况下分担参数与计算。它不是单一算法，切分轴决定通信模式。

讲义用一页开篇图交代这一节的**定位**与**路线图**：

![模型并行总览：像 ZeRO-3 一样切参数，但传的是激活；分支为 PP / TP(+SP) / EP](assets/lecture08-model-parallel-overview.png)

图：§3 开篇页「Beyond data parallel – model parallelism」。两点值得记住：

- **定位差异**：数据并行靠加卡换**吞吐**（每卡不同样本）；模型并行在**不改变 batch size** 的前提下靠加卡换**容量**（每卡持有模型的不同部分）。
- **与 ZeRO-3 的异同**（本节最有用的一条对照）：

| | 参数 | 通信对象 |
| --- | --- | --- |
| **ZeRO-3 / FSDP** | 切到各卡 | **参数**（用时 all-gather 聚齐、用完释放） |
| **模型并行** | 同样切到各卡 | **激活**（参数固定在各自卡上，流动的是中间结果） |

- **三条路线**：**① Pipeline parallel**（按层切）、**② Tensor parallel + Sequence parallel**（按矩阵宽度 / 序列切）、**③ Expert parallel**（按专家切）——即"三种不同的切模型方式"。

记住上面这条对照，后面看 PP / TP / EP 的通信模式就有了统一坐标：**流动的是参数还是激活，决定了通信发生在计算图的哪个位置、频次有多高**。

### 先分清：FSDP 切的是"副本"，张量并行切的是"计算"

上一节的 ZeRO-3/FSDP 与本节的模型并行**都把参数切到多张卡上**，这是最容易混淆的地方。但两者切的东西和后果完全不同：

**1. FSDP / ZeRO-3 —— 切的是冗余副本**

- **本质**：解决 DDP 中"每张卡都存一份完整参数太浪费显存"。
- **切法**：把参数、梯度、优化器状态**平铺切碎**，每卡持 $1/N$ 分片。
- **关键动作**：计算某一层之前，必须 **all-gather** 把该层完整参数**临时拼回来**，算完立刻释放。
- **一句话**：FSDP **逻辑上模型仍是完整整体**——每张卡都在跑同样的前向/反向逻辑（只是处理不同数据）。它**不改变计算图，只改变存储方式**。

**2. 张量并行 / 模型并行 —— 切的是计算逻辑**

- **本质**：模型大到连**计算过程本身**都无法在单卡完成（矩阵乘过大，或运算中的中间结果装不下）。
- **切法**：把 $Y=XW$ 中的 $W$ **按计算维度**切开（按输出维列切或按输入维行切），**不是平铺切**。
- **关键动作**：GPU0 算 $Y_1=XW_1$，GPU1 算 $Y_2=XW_2$；**它们永远不会把 $W_1$、$W_2$ 拼成完整的 $W$**。各卡交换的是**部分结果（激活值）**：
  - **列切**：结果沿输出维分片，后续层直接消费分片（需要完整张量时才 all-gather 拼接）；
  - **行切**：各卡得到部分和，做 **all-reduce 相加**。
- **一句话**：张量并行**改变了计算图**——每张卡只负责计算图的一部分。

| | 切的是什么 | 计算时要不要拼回完整 $W$ | 改变计算图吗 |
| --- | --- | --- | --- |
| **FSDP / ZeRO-3** | 冗余副本（存储） | **要**（临时 all-gather，用完即释放） | 否，只换存储方式 |
| **张量并行** | 计算逻辑（矩阵维度） | **绝不** | 是，每卡只算一部分 |

**一个判断口诀**：问一句"**算的时候需不需要把完整权重聚回来？**"——需要就是 FSDP 那类（切存储），不需要、只传激活的就是模型并行那类（切计算）。

**面试速述：** 模型并行把权重和计算分布到不同卡，以激活或部分结果的传输换取单卡容量。按层深切形成 PP，按矩阵宽度切形成 TP；两者的通信频率和适合的链路不同。

### 流水线并行 PP：按层切分

把连续层分给 $p$ 个 stage，前向把激活发送给下一 stage，反向把激活梯度传回。若一次只处理一个 batch，任一时刻大部分 stage 等待其他 stage，利用率可低至约 $1/p$。把 batch 切成 $m$ 个 microbatch，stage 处理完一个 microbatch 就继续下一个，形成流水线。讲义对简单 flush 调度给出**气泡时间/有用计算时间约为 $(p-1)/m$**；相应理想利用率可写成 $m/(m+p-1)$。这个比值依赖等长 stage、稳定 microbatch 计算、忽略通信等假设，不是任意 1F1B/交错调度的精确值。

讲义用一页调度图把这条流水线画了出来（这里 $p=4$ 个 stage、$m=4$ 个 microbatch）：

![流水线并行调度：4 个 stage × 4 个 microbatch，F 前向 / B 反向 / Update 更新，中间留出 Bubble](assets/lecture08-pipeline-parallel-schedule.png)

图：讲义「A solution: pipeline parallel」一页。横轴是时间，纵轴是 4 个 stage（每个 stage 一个色系），格子标为 `F_{stage,microbatch}` 或 `B_{stage,microbatch}`：

- **前向**：`F0,0` 先进入 stage 0；算完把激活发给 stage 1，**同时 stage 0 立刻开始 `F0,1`**——即讲义所说的 “Send off the first microbatch and start computing the second”。
- **反向**：所有 microbatch 的前向都走完后，按**相反顺序**回流，`B3,0 → … → B0,0`，各 stage 再各自 `Update`。
- **Bubble（气泡）**：图中央那块空白——在**填充**（后面的 stage 还没轮到活）和**排空**（前面的 stage 已无活可做）这两段时间里，设备在空转。

页面底部给出气泡占比，并解释了**为什么 PP 需要大 batch**：

$$\frac{\text{bubble time}}{\text{useful time}}=\frac{n_{\text{stages}}-1}{m}$$

要压小气泡，就得让 $m$ 远大于 $n_{\text{stages}}$；而 $m=\text{全局 batch}/\text{micro batch size}$，所以**要么全局 batch 足够大，要么把单个 microbatch 切小**。这与正文的 $(p-1)/m$ 是同一个式子（此处 $p=n_{\text{stages}}$）。

PP 的好处是每卡只放约 $1/p$ 层参数，并在相邻 stage 之间以点对点方式传大小约 $bsh$ 的激活（$b$ 为 microbatch 大小，$s$ 为序列长，$h$ 为 hidden size）；比每层都 collective 的 TP 更适合较慢的跨节点链路。代价是需要足够多 microbatch 填满流水线，以及保存/重算在途激活。讲义进一步提到交错流水线用更多通信换利用率；“zero bubble” 将反向拆成必须沿流水线传播的输入/激活梯度和可择机计算的权重梯度，借调度空隙填补气泡。它们都需要具体实现和资源预算，不能由公式直接保证零空闲。

讲义用一页把 "zero bubble" 的做法画清楚：

![Zero bubble 流水线：把反向拆成 B（激活梯度，须沿流水线传）与 W（权重梯度，可择机填入气泡）](assets/lecture08-zero-bubble-pipeline.png)

图：讲义「'Zero bubble' pipelining」一页。理解这张图只需抓住"**把反向劈成两半**"：

- **拆法**（图 1 的计算图）：

| 部分 | 算什么 | 能不能挪 |
| --- | --- | --- |
| **B** | 反向传激活梯度 $\partial L/\partial z$、$\partial L/\partial x$ | **不能**——必须按流水线逆序传回上一 stage |
| **W** | 计算权重梯度 $\partial L/\partial W$ | **能**——只依赖本 stage 自己的数据，所以讲义说 "The second part can be done whenever" |

- **图 2**（1F1B 调度，蓝 = Forward、橙 = Backward、米色 = Optimizer step）：前向填充与反向排空两段有明显空白，就是前面说的气泡。
- **图 3**（手工调度，上 **ZB-H1**、下 **ZB-H2**；蓝 = F、青 = B、绿 = W）：把 **W 块塞进那些空白**。越往下填得越满，代价是需要保存**更多在途激活/中间量**。

要点提醒：**"zero bubble" 里的 zero 指的是气泡，不是零开销**——换来的是更复杂的调度与更高的显存占用；只有在论文设定的条件成立时才接近零气泡，所以正文"不能由公式直接保证零空闲"这句依然成立，面试时不要把 zero bubble 说成"免费消掉气泡"。

**面试速述：** PP 把连续层分成 stage，前向传激活、反向传梯度，并用 microbatch 填流水线；简单等时 flush 调度的利用率约 $m/(m+p-1)$。它能分担层参数且通信集中在阶段边界，但微批次不足或阶段不均衡会产生气泡。

### 张量并行 TP：按矩阵宽度切分

对两层 MLP，令 $A=[A_1,A_2]$ 按**列**切、$B=[B_1;B_2]$ 按**行**切：

$$Y_i=\operatorname{GeLU}(XA_i),\qquad Z=\sum_iY_iB_i.$$

每卡算自己的 $Y_i$ 和 $Y_iB_i$，然后 all-reduce 部分和得到完整 $Z$。图中的 $f$ 在前向是恒等、反向是 all-reduce；$g$ 在前向是 all-reduce、反向是恒等。这解释了为什么列并行和行并行通常成对放置：非线性 GeLU 在各自列片上即可做，直到第二个矩阵乘后才需要合并。Transformer 内可把 QKV 和 MLP 上投影列切、注意力输出投影与 MLP 下投影行切；norm、router 等在该基础方案中复制。

TP 不需要 pipeline microbatch 来填气泡，但几乎每个 block 都要传激活规模的 collective，且计算通常要等待结果。讲义第 43 页用每层约 $8\frac{t-1}{t}bsh$ 的通信量与 PP 的每 microbatch 约 $bsh$ 点对点传输作量级对比；系数取决于是否包含前反向、何种激活与并行实现，不能当作所有架构的精确性能公式。GPU 上通常把 TP 约束在节点内高速互联域，讲义例子一般不超过 8 卡；越过慢链路时频繁同步会拖累速度。

**面试速述：** TP 将 MLP 第一矩阵按列、第二矩阵按行切，各卡独立做非线性，再对部分输出求和，减少过早汇聚。它在每个 block 都要做激活 collective，通常适合节点内快互连；讲义通信系数依实现假设而变。

## 4. 激活显存、专家与长上下文（第 44–54 页）

**面试速述：** 参数放下后，激活、MoE 专家和长上下文仍可能分别形成瓶颈。TP/SP 处理普通层的激活布局，EP 分布专家权重，CP 分担长序列注意力状态；它们切的维度不同，也各有通信代价。

### 先看清：显存不是静态的，参数只是冰山一角

讲义在进入激活记账之前，用一张 PyTorch 显存剖析图收束这个话题（横轴是训练步、纵轴是分配量）：

![训练过程显存随时间波动：静态的参数与优化器状态平铺在底部，激活与梯度呈山峰状起伏](assets/lecture08-dynamic-memory.png)

图：讲义「A final complexity – memory is dynamic!」一页（该例 Max allocated 0.53 GB / Max reserved 0.59 GB）。图例按用途分色，但更该按**静态 / 动态**两类来读：

| 类别 | 色块 | 随训练步的变化 |
| --- | --- | --- |
| **静态** | 绿 `PARAMETER`、黄 `OPTIMIZER_STATE` | 平铺在底部；模型不变就**恒定** |
| **动态** | 红 `ACTIVATION`、蓝 `GRADIENT` | **山峰状起伏**，要看**峰值**而不是均值 |

沿一个 step 读：

- **前向**：每层算完就把**激活值**留在显存里供反向使用 → 红色随层数**层层堆高**（上坡）。
- **反向**：算完一层就**释放**该层激活（下坡），同时**累积梯度** → 蓝色逐渐涨到顶。
- **Optimizer step**：图上那些灰色竖线是更新时刻——梯度清空，进入下一个 step，重新起一座山。

**为什么要单列这张图**：把"显存 = 参数量"当全部，是最天真的理解。训练大模型、尤其长序列或大 batch 时，**激活值往往超过参数本身**——这正是 §2 那份"每参数 16 字节"静态账本之外的部分，也是本节要分摊的对象。

它还能顺带解释前面几个"为什么"：

- **DDP 为什么显存不够**：每张卡除了绿色、黄色，还要各存一份完整的红色与蓝色。
- **FSDP 为什么要 all-gather**：为了算出这些红蓝部分，必须把完整参数**临时拼回来**。
- **zero bubble 为什么要更多显存**：把权重梯度（W）推迟计算，意味着**红峰必须保留更久**，山峰变宽、峰值可能更高——用 GPU 利用率换显存。

**一句话**：显存不只是"静态仓库"（参数 + 优化器状态），更是"动态施工现场"（激活 + 梯度）；而优化 GPU 利用率，常常是在往这个工地里堆更多东西。**先理解动态峰值，才谈得上分布式显存优化。**

### 按讲义模型推导激活公式

第 46–49 页引用特定 Transformer 实现的激活记账模型。下式单位随原文的激活精度/记账约定而定，适合比较缩放趋势，**不是通用网络结构的逐字节显存预测器**（符号含义见下方讲义原页的表格）：

$$M_{\rm no\ parallel}=sbh\left(34+5\frac{as}{h}\right).$$

讲义原页还给了公式里各符号的含义，后面 PP / CP 的公式会继续用到这张表：

![讲义原页：每层激活显存 sbh(34 + 5as/h)，以及公式中各符号的含义](assets/lecture08-activation-memory-formula.png)

图：讲义「What's the activation memory per layer?」一页。页面下方的符号表值得单独记住：

| 符号 | 含义 | 符号 | 含义 |
| :--- | --- | :--- | --- |
| $a$ | 注意力头数 | $p$ | 流水线并行度 |
| $b$ | microbatch 大小 | $s$ | 序列长度 |
| $h$ | hidden 维度 | $t$ | 张量并行度 |
| $l$ | Transformer 层数 | $v$ | 词表大小 |

页面上两条英文注解也值得单独记住：

- **“The $5\frac{as}{h}$ terms come from the quadratic attention terms incl dropout”** —— 二次项来自注意力矩阵与 dropout，随 $s^2$ 增长；
- **“As with flash attention, we can drop this term via recomputation”** —— 与 FlashAttention 同理，用**重计算**可以把这一项去掉。

TP 把可切的矩阵乘相关激活摊到 $t$ 卡，但留下一项不能靠 TP 缩小：

$$M_{\rm TP}=sbh\left(10+\frac{24}{t}+5\frac{as}{ht}\right).$$

$10sbh$ 由层归一化 $4sbh$、dropout $2sbh$、注意力与 MLP 输入 $4sbh$ 组成。随着 TP 度上升，固定的 10 项成为瓶颈。若配合选择性激活重计算，二次项去掉，剩 $sbh(10+24/t)$。

**面试速述：** 讲义的激活公式说明，单纯 TP 只缩小可分片项，归一化和 dropout 等仍留下 $10sbh$ 的固定激活项。选择性重计算可去掉该示例的二次项；这些系数来自特定 Transformer 记账，不能直接当通用逐字节预测。

### 序列并行 SP

![官方第 8 讲第 48 页的 TP 与 SP 布局切换示意图](assets/lecture08-p48-tensor-sequence-parallel.png)

图：Stanford CS336 Spring 2026 [Lecture 8 官方 PDF 第 48 页](https://github.com/stanford-cs336/lectures/blob/main/lecture_08.pdf#page=48)。图中的 $g$ 在前向为 all-gather，$\bar g$ 为 reduce-scatter；反向操作互换。该页未标注此示意图的第三方出处。

LayerNorm、dropout 等是对 token 逐点执行的操作，可以沿序列维把上述 10 项分给 TP 进程组。讲义图中，从序列切片进入需要完整输入的 TP 子层，前向用 all-gather；从 TP 子层回到序列切片，前向用 reduce-scatter，反向方向互换。于是该模型中

$$M_{\rm TP+SP}=sbh\left(\frac{34}{t}+5\frac{as}{ht}\right),\qquad
M_{\rm TP+SP+recompute}=sbh\frac{34}{t}.$$

这才使所列激活项随 $t$ 近似线性下降。SP 不是“额外复制出 $t$ 倍设备”：它通常利用既有 TP 进程组，在 TP 子层之间改变激活布局。公式没覆盖所有模型结构、残差缓冲及通信时的峰值。

**面试速述：** SP 补的是 TP 切不掉的那块——LayerNorm、dropout 等对每个 token 独立执行的**逐元素**操作，正是公式里的常数项（$10sbh$）。既然按 token 独立，就能沿**序列维**把激活切到 TP 组内的各卡，把完整的 $10sbh$ 摊成 $10sbh/t$，使单卡激活真正随 $t$ 线性下降。代价是布局切换通信：前向进入矩阵乘前要 **all-gather** 拼回完整序列，矩阵乘之后要 **reduce-scatter** 切回分片；反向时这两个操作正好反转。整体是**拿通信带宽换显存**；公式仍未覆盖所有结构与瞬时缓冲。

### 三招叠加：把激活压到 34sbh/t

把本节前面几件事串起来，就是训练大模型时压激活显存的**标准组合拳**：

| 手段 | 切 / 去掉什么 | 对公式的作用 |
| --- | --- | --- |
| **张量并行 TP** | 切矩阵乘（含注意力头），即 $24sbh$ 与二次项这块大头 | $24 \to 24/t$，$5as/h \to 5as/(ht)$ |
| **序列并行 SP** | 沿序列切 LayerNorm、dropout 等**逐元素**操作（切不动的固定项） | $10 \to 10/t$ |
| **选择性激活重计算** | 配合 FlashAttention，**不保存** $O(s^2)$ 的注意力大矩阵 | 二次项直接归零 |

三步走完：

$$sbh\Big(34+5\frac{as}{h}\Big)\xrightarrow{\ \rm TP\ }sbh\Big(10+\frac{24}{t}+5\frac{as}{ht}\Big)\xrightarrow{\ \rm SP\ }sbh\Big(\frac{34}{t}+5\frac{as}{ht}\Big)\xrightarrow{\ \rm 重算\ }sbh\frac{34}{t}$$

**面试绝杀版**：为把单卡激活压到最低，通常三招一起上——**TP** 切矩阵乘与注意力头，解决 $24sbh$ 与二次项这块大头；**SP** 沿序列维度切 LayerNorm / dropout 这类切不动的逐元素开销（$10sbh$）；**选择性重计算**结合 FlashAttention，干脆不保存 $O(s^2)$ 的注意力大矩阵，把平方项归零。三者叠加后激活显存化简为 $34sbh/t$，随 TP 度 $t$ 近似线性下降。这是当前训练长上下文、大参数模型的显存优化主线。

**但"线性"不等于"无限"**：$t$ 受节点内高速域（NVLink 域）规模限制，跨节点做 TP 的通信代价通常不划算；而且 $34sbh/t$ 只覆盖讲义这套记账里的激活项，残差缓冲、通信缓冲与瞬时峰值仍要另算。

### 专家并行 EP：按 MoE 专家切分

讲义第 50–53 页转向 MoE。路由器为 token 选专家；EP 把不同专家放到不同 GPU，先把 token 激活按目的专家 **all-to-all** 发送，执行各专家的 MLP，再把输出送回原 token 位置。它分摊的是**专家权重**，不是普通 dense attention 权重，也不直接减少所有激活显存。与把同一个大矩阵切开的 TP 相比，EP 让每个专家保留较完整的矩阵乘，计算效率可能更好；代价是路由通信不规则，专家负载可能失衡，还需每专家有足够 token 形成高效 batch。

**为什么专家层通常优先 EP 而不是 TP**：TP 按维度把同一个矩阵切开，每张卡上的 GEMM 因此**变小**；GEMM 一小，算术强度（每搬运 1 字节对应的 FLOPs）随之下降，容易从 **compute-bound 掉进 memory-bound**，再叠加每层都要做的 collective，利用率被双重拖累。EP 相反——**每个专家仍是完整的大矩阵**，GEMM 形状更大、更容易吃满算力。

需要说准的一点：EP 的通信量并不比 TP 小（一次 MoE 层要有 dispatch 与 combine **两次 all-to-all**）。它真正的优势在于**通信模式更适合重叠**——all-to-all 与专家 MLP 计算可以并行推进，这正是 DeepEP 这类实现的设计重点（见下）。

所以底层原则可以记成一句：**尽量让矩阵乘保持足够大的尺寸，避免过度切碎**。这也解释了为什么常见配置是「attention 用 TP、专家用 EP」——两者对切分粒度的偏好不同。

> 边界提醒：以上是**机制层面**的比较。具体到某个模型、某种硬件与实现，EP/TP 的最优配比必须实测；本文不引用未标明来源的加速比数字，也不把某组并行度的结论当成通用最优。

**澄清一个高频错点：all-to-all 不是"广播 + 本地筛选"。**

- **发送前先按目的专家分组**：每张卡把自己本地的 token 按路由器选中的专家重新排列。专家 $e$ 放在卡 $r(e)$ 上，于是"要发给第 $j$ 张卡的 token"构成一份与其他份**互不相交**的分片。
- **all-to-all 只搬分片**：rank $i$ 的第 $j$ 份只发给 rank $j$。因此每个 token **只被发送一次**，不是发给所有卡。
- **收到即可直接计算**：rank $j$ 收到的正好是"应由本地专家处理"的 token，不需要再从中筛掉别的专家的数据。

所以 dispatch 阶段每卡的通信量约为"本地 token 数 × 隐藏维"，**不是它的 $W$ 倍**。若理解成"全量发给所有人、各自再筛"，通信量会被高估 $W$ 倍——这是 MoE 通信估算里最容易算错的一处。

那"收到却不算"的直觉从哪来？来自**容量填充与丢弃**：专家缓冲通常按容量因子 $C$ 补齐，收到的槽位里可能有空位（padding）需要 mask 掉；超出容量的 token 会被丢弃或走旁路。被"无视"的是这些**空位与溢出 token**，而不是"别的专家的 token"。

课堂约 55:44 用 DeepEP 作为**特定实现案例**：一次 MoE 层通常包含 token dispatch 的 all-to-all、各专家 MLP 计算、结果 combine 的 all-to-all。该库展示 GPU/RDMA 通信 kernel 及与计算重叠的设计，讲者用它说明专家并行的工程复杂性，并未逐项讲解内部实现或验证通用加速倍数；不能把 DeepEP 的能力说成所有 EP 都自动具备。

讲义特别提醒：MoE 多用于 MLP，attention 与专家部分对 TP/EP 的偏好不同。系统可为 attention 设 TP/CP/DP，为专家设 ETP（Expert Tensor Parallelism，专家张量并行）、EP（Expert Parallelism，专家并行）、EDP（Expert Data Parallelism，专家数据并行）等不同维度；不能把每个层都机械地套进同一组轴。DP 与 EP 的副本关系，以及 DP×TP 对每卡 token 数和利用率的影响，也要按实际进程组检查。

**面试速述：** EP 把 MoE 专家权重分布到不同卡，token 经 all-to-all 送到选中专家、计算后再送回。它保留每个专家较完整的矩阵乘，却要求每专家有足够 token，且路由热点会造成负载不均；dense attention 仍需单独规划。

### 上下文并行 CP / Ring Attention

讲义第 54 页另列 CP：为超长上下文把整段输入序列切到多卡，注意力计算要交换别的卡的 K/V 块，或以 ring 方式逐块传递，使各卡的 query 与全局上下文交互。它主要分担长序列激活与 KV 占用，尤其在 $s$ 极大时有用；不同于 SP 主要分摊 LN/dropout 等逐 token 操作。CP 的通信取决于注意力实现、序列长度和切分度，不能假定单纯切序列后各 GPU 完全独立。讲义第 55 页的总表也将 SP/CP 归为“激活或 KV 分片，付出跨 rank 交换”。

**面试速述：** CP 为超长上下文切分整段序列，各卡须交换 K/V 块才能让本地 query 看到全局上下文；它主要缓解长序列激活和 KV 容量。SP 则主要分摊逐 token 操作，不能把两者都理解为切序列后零通信。

## 5. 组合并行维度与实际配置（第 55–73 页）

**面试速述：** 多维并行应从显存、激活、链路和每卡 token 数倒推：快链路承载高频 TP，PP 可按边界跨节点，最后用 DP 扩吞吐。真实系统还要核对进程组乘积、最慢 stage 和容错成本，公开配置只能当案例。

### 先确定瓶颈，再选择并行轴

讲义的经验顺序是：先使模型状态与激活放得下，再用剩余 GPU 增大数据并行吞吐。若节点内高速互联充足，可先用 TP（MoE 则结合 EP）；层数多、跨节点链路较慢时用 PP 切层；也可在带宽足够时选择 ZeRO-3/FSDP。长上下文优先检查激活/KV，考虑 SP、CP、FlashAttention 与重计算。最后再扩 DP；若每卡 microbatch 小，做梯度累积可扩大有效全局 batch、摊薄每次同步开销，但会改变优化过程中的有效 batch。

讲义第 56 页的 **4×4×4 网格模型**把每层计算时间除以通信时间，横轴是全局 batch 除以总芯片数 $B/N$。图中约 $B/N<400$ 时所比较的方案仍由通信主导；约 400–850 时，混合 FSDP（Fully Sharded Data Parallel，完全分片数据并行）+ MP（Model Parallelism，模型并行）跨过计算/通信分界，而纯 FSDP 尚未跨过；再增大到约 850 以上，两者都可能成为计算主导。纯 MP 的橙线在图示范围内始终低于计算/通信比 1，不能把“两个方案可行”误读成三个方案都可行。**这些是该图的模型与拓扑下的阈值，不是通用 batch 配置建议**：同一分片方案随每芯片工作量变化，优劣会反转，不能只按总 GPU 数选择并行轴。

![讲义第 56 页：不同并行方案随每芯片 batch 变化的计算/通信比](assets/lecture08-p56-model-vs-tensor-parallel.png)

*图源：[官方 Lecture 8 讲义第 56 页](https://github.com/stanford-cs336/lectures/blob/main/lecture_08.pdf#page=56)；表和曲线均为特定假设的示意，非通用阈值。*

对一个简单 dense 训练网格，常用总卡数记账为 $G=d\times t\times p\times c$（DP、TP、PP、CP 各轴相互独立时）；例如 256 卡若选 $t=8,p=4,c=1$，则 $d=8$。EP 的进程组可能与 DP 或 TP/ETP 交错，不应在不了解拓扑时无条件再乘一个 EP。还须核查：每个 stage 的层数与显存、每张卡的 microbatch/token 数、最慢 stage、所有 collective 所跨网络层级，以及故障重启/检查点成本。

第 59–62 页的 Megatron-LM 案例说明：模型增大时，TP 先升至 8 左右，之后主要增 PP 以放下更多层，DP 度可能下降；在给定 64 GPU、162.2B GPT 的实验中 $(p,t)=(8,8)$ 性能优于更极端的切法。该观察有指定模型、机器和 batch 条件，不能推成“TP=8 永远最优”。激活重计算虽增加 FLOPs，若因此能用更大 microbatch、减少气泡或改善吞吐，整体训练反而可能更快。

讲义第 58 页摘录的 Megatron 建议把这个取舍落到网络域：在避免 OOM 的前提下尽量少用模型并行、保留较大的 DP；常规情况下让 EP×TP 位于单节点 NVLink 域内（示例为 8 卡），跨节点扩展优先切 PP；当 $PP\ge2$ 时可用虚拟流水线 stage 缩小气泡。专家层优先考虑 EP 而非盲目增 TP，图中的 Mixtral 8×7B 示例为 EP8×TP1 优于 EP4×TP2；序列长到约 8K token 及以上时可考虑 CP，但收益仍依赖计算/通信重叠。图也特别提醒：超大 MoE 的 EP 通信甚至可超过节点内链路能力，需要让跨节点 all-to-all 与计算重叠。这些均是**该讲义转述的具体系统经验**，不是任意硬件上的固定配方。

第 60 页另一张实测图对比固定全局 batch 下的 175B 与 530B 模型：只用 ZeRO-3、不断扩大 GPU 数时，单卡 achieved TFLOP/s 明显下降；将 TP、PP、DP 组合的 PTD-P 方案则保持相对平坦的单卡吞吐。这补足了“分得下”与“扩得快”的区别：纯分片能解决容量，却未必让通信随规模保持可控；曲线只证明该实验配置的表现，不能推断所有 FSDP 实现都如此。

2. 为什么 all-reduce 可以拆为 reduce-scatter 与 all-gather？若每 rank 梯度张量是 4 GB、$N=8$，理想环算法的每设备传输量约多少？

5. 在第 46–49 页模型中，令 $s=2048,b=1,h=4096,a=32,t=8$。分别写出 TP 与 TP+SP+选择性重计算的激活表达式；哪个项即使 $t$ 增大也不会通过单纯 TP 下降？
6. 同一训练集群中，哪些通信适合放在节点内高速域，哪些可跨较慢节点间链路？若 MoE 有 token 热点，EP 还需要检查什么？

参考答案：① 每卡分别为 $160$、$(4+12/8)\times10=55$、$(2+14/8)\times10=37.5$、$16/8\times10=20$ GB；均未算激活、临时参数副本等。② all-reduce 的全量结果由各 rank 的 reduce-scatter 分片拼合；$2(7/8)\times4=7$ GB/设备。③ $3/8=37.5\%$，利用率 $8/11\approx72.7\%$；$m=2$ 时比值 $3/2$、利用率 $2/5=40\%$。④ 各卡先独立算 $Y_i=\operatorname{GeLU}(XA_i)$，再对 $Y_iB_i$ 求和；合并发生在第二个矩阵乘之后，非线性不需事先合并。⑤ $M_{\rm TP}=sbh(10+24/8+5as/(8h))$；$M_{\rm TP+SP+recompute}=34sbh/8$；固定的 $10sbh$ 是单纯 TP 的瓶颈。⑥ TP 高频 collective 宜在快链路；PP 相邻 stage 的激活点对点传输可跨节点，仍需以实测带宽和延迟评估；EP 要看 token 数/专家、负载偏斜与 all-to-all 带宽。

**本节小结：** 练习用显存记账、collective 流量、气泡、激活公式和拓扑选择检验是否会按假设推导，并提醒理论容量与真实可训练容量不同。

## 7. 心智模型小结：先找瓶颈，再选切分轴

本讲最实用的心智模型，可压缩成三句：

1. **先看瓶颈在哪，再选切分轴。** 放不下才去切模型状态（ZeRO/FSDP、TP、PP），放得下就先用 DP 换吞吐。
2. **快链路干高频通信，慢链路干低频通信。** TP 的每层 collective 留在节点内高带宽域；PP 阶段边界、DP 的梯度同步可跨较慢的节点间链路。
3. **分得下不等于扩得快。** 显存够只是“能跑”，加速比还要看通信占比、气泡与负载是否均衡。

各类并行一句话对照：

| 并行方式 | 切什么 | 主要通信 | 适合链路 |
| --- | --- | --- | --- |
| DP | 样本 | 梯度 all-reduce（约 $2P$） | 可跨节点 |
| ZeRO-1/2 | 优化器状态 / 梯度 | reduce-scatter + all-gather（约 $2P$） | 可跨节点 |
| ZeRO-3 / FSDP | 参数也切 | 前向/反向 all-gather + reduce-scatter（约 $3P$） | 可跨节点 |
| PP | 层 | 阶段边界点对点传激活 | 可跨节点 |
| TP | 矩阵宽度 | 每层激活 collective | 节点内快链路 |
| SP | 逐 token 激活 | all-gather / reduce-scatter | 复用 TP 组 |
| EP | 专家 | all-to-all | 可跨节点，但路由难 |
| CP | 序列 | K/V 交换 | 长上下文 |

> **易错点：** DP 与 ZeRO-1/2 的每步通信量都在 $2P$ 量级，**差别主要在显存而非通信**——ZeRO 省掉的是优化器状态与梯度的副本。不要因为“用了 ZeRO”就认为通信更少，这是面试里常见的误答。

最后记住三本账：

- **显存账**：参数、梯度、优化器状态、激活，各占多少？
- **通信账**：每步传多少？跨哪级链路？
- **空闲账**：气泡、负载不均、等待通信，浪费了多少？

不能只凭“GPU 数量翻倍”预测加速。

**本节小结：** 先用三句口诀定方向，再用总表对照切分轴与链路，最后用显存/通信/空闲三本账检验结论，避免把“能放下”当成“扩得快”。
