# Agent 完整知识体系

## 一、Agent 基础认知

- 核心定义
  - 全称：智能体（Agent）
  - 核心解决：LLM「只会说不会做」问题（纯生成模型无法自主行动）
  - 本质：给 LLM 装上「手脚」和「大脑循环」——能感知、能决策、能行动、能迭代
- 与纯 LLM 的本质区别
  - 纯 LLM：输入 → 输出，一次生成，无行动能力
  - Agent：输入 → 思考 → 行动 → 观察 → 再思考 → 直到完成，多轮自主循环
- 解决的三大核心问题
  - 任务执行：不只是回答，而是实际完成多步骤任务
  - 工具使用：调用外部 API、数据库、搜索引擎、代码执行器
  - 自主决策：根据中间结果动态调整策略，而非一次性生成
- 核心价值
  - 任务自动化：把复杂流程交给 Agent 自主完成
  - 能力扩展：通过工具接入 LLM 本身不具备的能力（计算、搜索、执行）
  - 动态适应：根据环境反馈调整行为，而非固定流程

## 二、Agent 完整工作流程

- 核心循环（ReAct 范式）
  - Thought：思考当前状态和下一步
  - Action：选择并调用工具
  - Observation：获取工具返回结果
  - 循环直到任务完成或达到终止条件
- 典型流程
  - 任务接收：接收用户目标
  - 任务规划：拆解为子任务或步骤序列
  - 工具选择：为每个步骤选择合适工具
  - 执行与观察：调用工具，获取结果
  - 反思与调整：根据结果决定继续、修正还是终止
  - 结果输出：汇总生成最终答案
- 关键认知
  - Agent 的核心不是「一次做对」，而是「错了能改」
  - 循环控制（何时停止）比单步执行更重要
  - 工具描述质量直接决定 Agent 能否正确选择工具

### 2.1 单轮 Agent vs 多轮 Agent

- 单轮 Agent
  - 一次思考 + 一次工具调用 + 一次生成
  - 适合简单任务：查天气、算数、单次检索
  - 实现简单，延迟低，但无法处理多步骤任务
- 多轮 Agent
  - 多轮 Thought-Action-Observation 循环
  - 适合复杂任务：研究、编码、多步推理
  - 需要循环控制、状态管理、错误恢复
- 工程门槛认知
  - 单轮 Agent 跑通只需几小时
  - 多轮 Agent 调稳需要数周，核心难点在循环控制和错误恢复

## 三、核心组件详解

### 3.1 规划（Planning）策略

- 核心问题：Agent 如何把复杂任务拆解为可执行的步骤
- 主流规划方法
  - ReAct：边想边做，每步根据观察调整
  - Plan-and-Execute：先制定完整计划，再逐步执行
  - Tree of Thoughts：多路径探索，选择最优分支
  - Reflexion：执行后反思失败原因，下次改进
- 规划能力的演进层次
  - CoT（Chain of Thought）：线性推理，一步步往下推，适合简单推理
  - ToT（Tree of Thoughts）：多路径探索，树状分支，适合需要试错的问题
  - GoT（Graph of Thoughts）：图结构分支合并，允许子结果聚合，适合复杂推理
  - Think in Code：让模型写代码而非自然语言来做规划，推理过程可执行、可验证、可控
  - 演进逻辑：从线性→树状→图状，从不可验证的自然语言→可执行代码
- ReAct vs Plan-and-Execute 的选型
  - ReAct 适合
    - 任务步骤不确定，需要边走边看
    - 中间结果会显著影响下一步决策
    - 探索型任务：调研、排查、开放问答
    - 短任务：步骤少，重规划成本低
  - Plan-and-Execute 适合
    - 任务结构清晰，可提前拆解
    - 步骤之间依赖关系明确
    - 长任务：提前规划避免中途迷失
    - 执行成本高，需要先确认计划再动手
  - 混合模式
    - 先 Plan-and-Execute 粗规划，执行中每步用 ReAct 动态调整
    - 生产系统常用：粗粒度计划 + 细粒度 ReAct
  - 常见误区
    - 什么任务都用 ReAct：长任务容易迷失，步数失控
    - 什么任务都用 Plan-and-Execute：计划一旦过时，后续全错
    - 正解：按任务确定性程度选，不确定就 ReAct，确定就 Plan
- 规划粒度权衡
  - 规划太粗：步骤模糊，执行时容易迷失
  - 规划太细：僵化，无法应对中间结果变化
  - 推荐：粗粒度规划 + 执行中动态细化
- 规划失败的回退
  - 计划无法执行时，重新规划而非硬走
  - 设置最大重规划次数，避免无限循环
- 任务拆分的工程细节
  - 拆分的三个验收标准
    - 完备性：拆出的子任务合起来覆盖原始目标，无遗漏
    - 独立性：子任务之间低耦合，可独立执行和验证
    - 可验证性：每个子任务有明确的完成标准，能判断是否做完
  - DAG 依赖图
    - 把子任务组织成有向无环图，识别依赖关系
    - 无依赖的步骤可以并行执行，显著降低总耗时
    - 有依赖的步骤必须串行，前一步输出是后一步输入
  - 动态 Replan 触发机制
    - 触发条件：工具连续失败、结果与预期严重不符、发现新信息推翻原假设
    - 不是每步都重规划，而是满足触发条件才重规划
    - 重规划要设置最大次数，避免陷入「规划-失败-再规划」的死循环

### 3.2 工具使用（Tool Use）

- 工具定义
  - 名称、描述、参数 schema、返回值格式
  - 描述质量直接决定 LLM 能否正确选择工具
- 工具选择策略
  - 全量注入：所有工具描述塞进 Prompt，适合工具少（<20）
  - 检索式选择：工具多时先检索相关工具，再注入
  - 分层路由：先选工具类别，再选具体工具
- 工具调用格式
  - JSON Schema 定义参数
  - Function Calling / Tool Calling 原生支持
  - 文本解析兜底（模型不支持原生调用时）
- 工具设计原则
  - 单一职责：一个工具只做一件事
  - 描述清晰：说清什么时候用、什么时候不用
  - 错误友好：返回结构化错误，便于 Agent 理解
- 常见工具类型
  - 搜索：Web 搜索、知识库检索
  - 计算：代码执行、计算器
  - 数据：SQL 查询、API 调用
  - 行动：发邮件、创建工单、操作浏览器
- 工具连接标准：MCP
  - 全称：Model Context Protocol，Anthropic 主导
  - 解决的问题：Agent 连工具
  - 核心价值：把工具接入标准化，不同 Agent 框架可复用同一套工具
  - 定位：工具侧的「USB-C 接口」
- Function Calling vs MCP 的配合关系
  - Function Calling：模型侧能力，让 LLM 输出结构化的工具调用请求
  - MCP：工程侧协议，定义工具如何被发现、描述、调用、返回
  - 两者不是替代关系，是不同层
    - Function Calling 解决「模型怎么表达要调用工具」
    - MCP 解决「工具怎么标准化接入、跨框架复用」
  - 典型配合
    - MCP Server 暴露工具 → Agent 框架通过 MCP Client 发现工具 → 把工具描述转成 Function Calling 格式注入模型 → 模型输出调用请求 → 框架通过 MCP 调用真实工具
  - 常见误区
    - 以为 MCP 替代 Function Calling：两者不在同一层，无法替代
    - 以为用了 MCP 就不需要 Function Calling：模型侧仍需 Function Calling 来表达调用意图
- 工具返回结果太大的截断策略
  - 问题本质：工具返回内容可能远超上下文窗口，直接塞进去会挤爆
  - 截断策略
    - 按长度截断：简单粗暴，但可能截掉关键信息
    - 按结构截断：JSON 保留关键字段，列表保留前 N 条
    - 摘要压缩：用小模型对返回结果做摘要，保留语义
    - 分页读取：告诉 Agent「结果太长，需要分页」，让 Agent 主动决定读哪部分
  - 选择原则
    - 结构化数据：按结构截断，保留关键字段
    - 文本数据：摘要压缩 + 关键片段保留
    - 不确定时：分页 + 让 Agent 决定
  - 工程注意
    - 截断必须告知 Agent「结果被截断了」，避免 Agent 以为看到了全部
    - 截断策略要按工具类型定制，不能一刀切

### 3.3 记忆（Memory）

- 核心问题：Agent 如何在多轮循环中记住上下文和历史
- 短期记忆
  - 当前任务的对话历史和中间结果
  - 滑动窗口 / 摘要压缩 / 关键信息抽取
- 长期记忆
  - 核心定义：跨会话的知识和经验，向量库存储 + 检索召回
  - 三种子类型
    - 情节记忆（Episodic）：过往具体经历，如「上次用户问过类似问题，我这样解决的」
    - 语义记忆（Semantic）：通用规律和事实，如「用户偏好简洁回答」
    - 程序记忆（Procedural）：操作 SOP 和技能，如「处理退款的标准流程是……」
  - 合理记忆粒度
    - 一次完整交互：适合情节记忆，记录完整的任务上下文
    - 一个独立知识点：适合语义记忆，一条规律一个条目
    - 不要太碎：碎到单个词没有检索价值
    - 不要太粗：粗到一整段对话无法精确召回
  - 记忆闭环的整合操作
    - 去重：相同或高度相似的记忆合并，避免冗余
    - 冲突消解：新旧记忆矛盾时，按时间/置信度决定保留哪个
    - 抽象提炼：从多条具体经验中抽象出通用规律，存入语义记忆
  - 主流开源记忆组件
    - Mem0：专注长期记忆的存储与检索
    - Letta（原 MemGPT）：把记忆管理做成操作系统式的分层架构
    - Zep：面向 Agent 的记忆服务，支持时序和会话管理
- 工作记忆
  - 当前任务的中间状态（已完成的步骤、待办事项）
  - 结构化存储，便于 Agent 随时查询
- 记忆管理策略
  - 什么该记：任务状态、关键决策、用户偏好
  - 什么该忘：冗余中间结果、失败尝试的细节
  - 何时压缩：接近上下文窗口上限时

### 3.4 反思与自我修正（Reflection）

- 核心问题：Agent 如何知道自己做错了，并改正
- 反思层次
  - 步骤级：当前步骤结果不对，立即修正
  - 任务级：整体方向偏了，重新规划
  - 跨任务级：从失败中学习，下次避免
- 反思触发条件
  - 工具返回错误
  - 结果与预期不符
  - 达到最大步数仍未完成
- 反思方法
  - Self-Refine：生成后自我批评再改进
  - Reflexion：失败后总结原因，存入记忆
  - 外部验证：用另一个模型或规则校验结果
- Self-Refine vs Reflexion 的区别与选型
  - Self-Refine
    - 时机：单次任务内，生成后立即自我批评
    - 作用范围：当前这一次输出
    - 是否跨任务：不跨任务，改完就结束
    - 适合：输出质量需要打磨，但任务本身没失败
    - 例子：写文案、生成代码，第一版不完美，自我批评后改进
  - Reflexion
    - 时机：任务失败后，总结失败原因
    - 作用范围：跨任务，把教训存入长期记忆
    - 是否跨任务：跨任务，下次遇到类似任务时召回
    - 适合：任务失败，需要从失败中学习
    - 例子：Agent 连续三次工具调用失败，反思「这个工具需要先鉴权」，存入记忆
  - 选型判断
    - 任务成功但质量不够 → Self-Refine
    - 任务失败需要总结教训 → Reflexion
    - 两者可以组合：先用 Self-Refine 打磨输出，失败后再用 Reflexion 总结
- 反思的硬性上限
  - 必须设置 2~3 轮最大反思次数
  - 防止模型陷入「为改而改」的死循环
  - 反思不是越多越好，超过阈值后边际收益为负

### 3.5 循环控制与终止条件

- 核心问题：Agent 什么时候该停
- 终止条件
  - 任务完成：Agent 判断目标已达成
  - 最大步数：硬性上限，防止无限循环
  - 最大时间：超时终止
  - 最大成本：token 或 API 调用预算耗尽
  - 连续失败：连续 N 次无进展则终止
- 循环失控的典型表现
  - 反复调用同一工具无进展
  - 在两个方案之间反复横跳
  - 不断重新规划但从不执行
- 防御策略
  - 设置硬性上限（步数、时间、成本）
  - 检测重复动作，强制跳出
  - 无进展检测：连续 N 步无新信息则终止
- ReAct 循环的本质
  - 循环是外层代码框架驱动的，不是模型自己在循环
  - 模型只负责每步的 Thought/Action 生成
  - 代码框架负责：调用模型、解析输出、执行工具、拼回 Observation、判断是否继续
  - 理解这一点，才能理解为什么循环控制必须在代码层做，不能只靠 Prompt

### 3.6 生成与 Prompt

- System Prompt 构造
  - 角色定义：Agent 是什么、能做什么
  - 工具说明：可用工具及使用场景
  - 约束条件：不能做什么、边界在哪
  - 输出格式：Thought/Action/Observation 格式要求
  - 终止条件：什么时候应该停止
- 关键 Prompt 工程
  - 工具描述要让模型知道「什么时候用」
  - 少样本示例（Few-shot）显著提升工具选择准确率
  - 明确要求「不确定时先问，不要瞎猜」
- 上下文工程
  - 中间结果太多时压缩历史
  - 关键信息前置，避免 Lost in the Middle
  - 工具返回结果截断，避免塞爆上下文

## 四、Agent vs 工作流 vs Agentic Workflow

- 本质区别
  - 工作流：预定义流程，步骤固定，LLM 只在固定节点做固定事
  - Agent：动态决策，步骤由 LLM 自主决定
  - Agentic Workflow：介于两者之间，流程有预定义骨架，但节点内由 LLM 自主决策
- 工作流优劣势
  - 优势：可控、可预测、易调试、成本低
  - 劣势：无法应对未预见的场景，灵活性差
- Agent 优劣势
  - 优势：灵活，能处理开放任务
  - 劣势：不可控、难调试、成本高、可能失控
- Agentic Workflow 优劣势
  - 优势：兼顾可控性和灵活性，是当前生产落地的主流形态
  - 劣势：设计复杂度高于纯工作流，需要判断哪些节点该放权给 LLM
- Anthropic 五种标准 Workflow 编排范式
  - Prompt Chaining（链式）
    - 前一步输出是后一步输入，串行执行
    - 适合：任务可清晰拆解为固定步骤
  - Routing（路由）
    - 按输入类型分发给不同处理器
    - 适合：输入类型多样，每种类型有专门处理逻辑
  - Parallelization（并行）
    - 多个子任务同时执行，结果汇总
    - 适合：子任务之间无依赖，可并行提速
  - Orchestrator-Workers（编排-工人）
    - 一个主 Agent 动态分派任务给多个 Worker
    - 适合：任务复杂，需要动态决定分派什么、分派给谁
  - Evaluator-Optimizer（评估-优化）
    - 生成后由评估者反馈，优化者改进，循环直到达标
    - 适合：输出质量要求高，需要多轮打磨
- 工程组合最佳实践
  - 能工作流解决的就不要用 Agent
  - 工作流处理确定性流程，Agent 处理开放性决策
  - Agentic Workflow 是生产主流：骨架用工作流，节点内用 Agent
  - 选型：流程固定选工作流，任务开放选 Agent，复杂生产系统用 Agentic Workflow

## 五、高级 Agent 范式

- ReAct：思考-行动-观察循环，最基础的 Agent 范式
- Plan-and-Execute：先规划再执行，适合长任务
- Reflexion：执行后反思，从失败中学习
- Tree of Thoughts：多路径探索，适合需要搜索的问题
- LATS（Language Agent Tree Search）：结合 MCTS 的 Agent 搜索
- Multi-Agent（多智能体）
  - 多个 Agent 分工协作
  - 常见架构：Orchestrator-Worker、辩论式、流水线式
  - Orchestrator-Worker vs 辩论式的选型
    - Orchestrator-Worker（编排-工人）
      - 结构：一个主 Agent 分派任务，多个 Worker 执行
      - 适合：任务可拆解，子任务相对独立
      - 优势：结构清晰，可控性强，易于调试
      - 劣势：主 Agent 是瓶颈，主 Agent 决策错了整体就错
      - 典型场景：研究助手、内容生产流水线
    - 辩论式（Debate）
      - 结构：多个 Agent 各自给出方案，互相批评，最终收敛
      - 适合：需要多视角、开放式问题、质量要求高
      - 优势：多视角互补，减少单点偏差
      - 劣势：通信开销大，收敛慢，成本高
      - 典型场景：复杂决策、方案评审、事实核查
    - 选型判断
      - 任务可清晰拆解 → Orchestrator-Worker
      - 任务需要多视角碰撞 → 辩论式
      - 生产系统多数用 Orchestrator-Worker，辩论式偏研究
  - Agent 间协作机制
    - 消息传递（Message Passing）
      - Agent 之间点对点发消息，解耦
      - 适合：独立并行任务，Agent 之间不需要共享中间状态
      - 优势：解耦、灵活、易扩展
      - 劣势：全局状态难追踪，复杂流程协调成本高
    - 共享状态（Shared State / Blackboard）
      - 多个 Agent 读写同一个状态存储
      - 适合：流水线型任务，Agent 之间有明确的上下游依赖
      - 优势：状态集中、易追踪、协调简单
      - 劣势：耦合高，并发写入需要同步机制
    - 选型判断
      - 独立并行任务 → 消息传递
      - 流水线型任务 → 共享状态
      - 生产系统常混合使用：主干用共享状态，分支用消息传递
  - 通信开销的控制
    - 问题本质：Agent 之间通信的消息量随 Agent 数量和轮次快速增长
    - 控制手段
      - 限制轮次：辩论式设最大轮次，避免无限辩论
      - 消息压缩：Agent 间传递摘要而非完整上下文
      - 共享状态：用共享黑板/状态而非点对点消息
      - 分层通信：只在必要时跨层通信，同层少通信
      - 异步通信：非阻塞消息传递，避免等待
    - 工程注意
      - 通信开销是 Multi-Agent 成本的主要来源之一
      - 设计时先问「这条消息真的需要传吗」
  - 核心挑战：通信协议、角色划分、冲突解决
  - 选型标准：什么时候必须用 Multi-Agent
    - 单 Agent 上下文撑爆：任务信息量超过单 Agent 上下文窗口
    - 需要跨领域专业分工：不同子任务需要不同的专业 Prompt 和工具集
    - 存在可并行子任务：子任务之间无依赖，可并行执行提速
    - 注意：不是「任务复杂就上多 Agent」，复杂但串行、同领域的任务，单 Agent 更合适
  - 为什么工程上几乎不用去中心化多 Agent
    - 无全局协调：每个 Agent 各自决策，无法保证整体目标一致
    - 无顺序保证：多个 Agent 并发行动，无法保证执行顺序
    - 无失败感知：一个 Agent 失败了，其他 Agent 不知道，整体任务可能已经跑偏
    - 生产级方案几乎都是中心化编排，而非去中心化协商
  - 当前生产级标准方案
    - LangGraph 图编排 + 状态检查点持久化
    - 图编排：把多 Agent 协作定义成有向图，节点是 Agent，边是流转条件
    - 状态检查点：每一步的状态持久化，长流程崩溃后可从断点续跑
    - 解决的核心问题：长流程崩溃断点续跑，这是 Multi-Agent 生产落地的关键
- Agentic RAG
  - Agent 自主决定何时检索、检索什么、是否重新检索
  - 与单次 RAG 的区别：多轮检索、动态调整查询
- Computer Use / Browser Use
  - Agent 直接操作浏览器或桌面
  - 核心挑战：界面理解、操作精度、错误恢复
- 具身 Agent（Embodied Agent）
  - Agent 控制物理实体（机器人）
  - 核心挑战：实时性、安全性、物理世界的不确定性
- Agent 间通信标准：A2A
  - 全称：Agent-to-Agent Protocol，Google 主导，已捐 Linux 基金会
  - 解决的问题：Agent 连 Agent，跨框架、跨平台的 Agent 通信
  - 与 MCP 的互补关系
    - MCP：Agent 连工具，工具侧标准
    - A2A：Agent 连 Agent，协作侧标准
    - 两者并列，构成 Agent 生态的两条标准线
  - 核心价值：不同框架实现的 Agent 可以互相发现、通信、协作，不被单一框架绑定
  - 定位：Agent 协作侧的「通用语言」

## 六、Agent 安全与风险防控

- 核心风险来源
  - 工具滥用：Agent 调用了不该调用的工具
  - 权限越界：Agent 执行了超出授权的操作
  - 提示注入：外部内容中的恶意指令被 Agent 执行
  - 无限循环：Agent 陷入死循环，消耗大量资源
  - 不可逆操作：删数据、发邮件、转账等无法撤销
- 分层防控
  - 基础必做：工具白名单，只允许调用预定义工具
  - 权限控制：每个工具设置权限边界，敏感操作需人工确认
  - 循环控制：硬性步数/时间/成本上限
  - 人工确认：不可逆操作必须经过人工审批
  - 审计日志：记录每一步决策和工具调用，便于追溯
- 提示注入的特殊危险性
  - Agent 会读取外部内容（网页、文档、API 返回）
  - 这些内容中的恶意指令可能被 Agent 当作任务执行
  - 与 RAG 间接注入同理，但 Agent 有行动能力，危害更大
  - 核心认知：Agent 的输入过滤不能只做用户输入，必须同时做工具返回内容过滤
- 沙箱与隔离
  - 核心问题：Agent 执行的代码或操作，如何不影响到宿主系统
  - 隔离级别选型
    - 进程级隔离：独立进程运行，适合低风险操作
      - 优势：开销小，实现简单
      - 劣势：隔离不彻底，仍可访问文件系统和网络
    - 容器级隔离（Docker）：独立文件系统 + 网络命名空间
      - 优势：隔离较彻底，开销可控
      - 劣势：内核共享，存在逃逸风险
      - 适合：大多数生产场景的默认选择
    - 虚拟机级隔离（VM）：独立内核 + 独立资源
      - 优势：隔离最彻底
      - 劣势：开销大，启动慢
      - 适合：高风险代码执行、多租户强隔离
    - 微虚拟机（Firecracker/gVisor）：介于容器和 VM 之间
      - 优势：接近 VM 的隔离 + 接近容器的开销
      - 适合：Serverless 代码执行、Agent 代码沙箱
  - 隔离级别怎么定
    - 按代码来源：用户输入的代码 → 高隔离；系统内置代码 → 低隔离
    - 按操作类型：只读操作 → 低隔离；写操作/网络操作 → 高隔离
    - 按租户：单租户 → 容器级；多租户 → 微虚拟机或 VM
    - 按合规：金融/医疗 → 高隔离 + 审计日志
  - 沙箱的工程要点
    - 资源限制：CPU、内存、磁盘、网络带宽上限
    - 超时控制：硬性执行时间上限
    - 网络白名单：只允许访问预定义域名
    - 文件系统只读：除特定临时目录外，其余只读
    - 审计日志：记录所有执行的代码和操作
  - 常见误区
    - 只做进程隔离就以为安全：进程隔离无法防文件系统和网络访问
    - 沙箱内不设资源上限：Agent 可能跑出无限循环耗尽资源
    - 沙箱和主系统共享敏感凭证：沙箱逃逸后凭证直接泄露

### 6.1 不可逆操作的确认机制

- 核心问题：Agent 执行了无法撤销的操作，造成实际损失
  - 删除数据、发送邮件、提交订单、转账
- 为什么危险
  - LLM 可能误解意图，执行了用户没想做的操作
  - 提示注入可能诱导 Agent 执行恶意操作
  - 一旦执行，无法回滚
- 防御策略
  - 操作分级：可逆操作自动执行，不可逆操作需确认
  - 人工确认：不可逆操作前必须经过用户明确批准
  - 预演模式：先展示「将要执行什么」，用户确认后再执行
  - 双人复核：高敏感操作需要两个独立确认
- 工程注意
  - 确认机制不能只靠 Prompt，必须在系统层强制
  - 确认信息要说清「做什么、影响什么、能否撤销」

## 七、Agent 效果评估

- 任务层评估
  - 任务完成率：Agent 是否完成了用户目标
  - 步骤效率：用了多少步完成，是否走了弯路
  - 工具调用准确率：是否选对了工具、传对了参数
- 过程层评估
  - 规划质量：任务拆解是否合理
  - 反思有效性：出错后是否能自我修正
  - 循环控制：是否在合理步数内终止
- 成本层评估
  - Token 消耗
  - 工具调用次数
  - 端到端延迟
- 评估方法
  - 人工评估：看完整轨迹，判断质量
  - 自动评估：用 LLM 判断任务是否完成
  - 基准测试：AgentBench、WebArena、SWE-bench
- 评估数据集
  - 构建任务集，覆盖不同难度和类型
  - 标注成功标准和关键步骤
  - 难例挖掘：重点测边界情况
- 线上核心指标
  - 任务完成率、平均步数、工具调用失败率
  - 用户干预率（用户中途纠正）
  - 成本超支率
- Bad Case 分层归因
  - 规划问题：任务拆解错误
  - 工具问题：选错工具或参数错误
  - 反思问题：出错后无法修正
  - 控制问题：循环失控或过早终止
  - 安全问题：执行了不该执行的操作

## 八、Agent 记忆与状态管理

- 核心挑战：多轮循环中，如何管理不断增长的上下文
- 状态管理
  - 任务状态：当前在做什么、已完成什么、待办什么
  - 工具状态：已调用哪些工具、返回了什么
  - 用户状态：用户偏好、历史交互
- 上下文压缩策略
  - 滑动窗口：只保留最近 N 步
  - 摘要压缩：对历史做摘要
  - 结构化存储：把关键状态抽出来单独存，不塞进 Prompt
- 跨会话记忆
  - 长期记忆存储：向量库 + 结构化数据库
  - 召回时机：任务开始时加载相关记忆
  - 更新时机：任务结束后写入新经验
  - 整合操作：去重、冲突消解、抽象提炼（详见 3.3 长期记忆）
- 冷启动与记忆稀疏
  - 新用户无历史记忆时，走默认策略
  - 不要强行召回不相关的历史记忆
  - 设置记忆质量阈值，低于阈值不召回

  - 记忆存储服务
  - LLM 服务

  - 每一步的 Thought/Action/Observation 全记录
  - 工具调用成功率、延迟、错误分布
  - 循环步数分布、终止原因分布
  - 成本消耗
- 全链路可观测性拆解
  - 核心：Agent 链路必须拆成每一步单独埋点
  - 每一步单独埋点

### 9.1 Agent 可观测性与调试（开发者视角）

- 与运维监控的区别
  - 运维监控：关注线上指标——成功率、延迟、成本、告警
  - 开发者调试：关注单次执行的轨迹——为什么这么走、哪一步出了问题
  - 两者互补，不能互相替代
- 核心能力
  - 轨迹回放（Trajectory Replay）
    - 把一次 Agent 执行的完整 Thought→Action→Observation 序列回放出来
    - 支持逐步前进、后退、跳转
    - 用途：定位哪一步决策错了、哪一步工具调用异常
  - 中间状态注入
    - 在回放时修改某一步的 Observation，看 Agent 会怎么走
    - 用途：验证「如果当时工具返回的是另一个结果，Agent 会不会做对」
    - 价值：区分「工具问题」还是「决策问题」
  - 对比调试（Diff Debugging）
    - 同一任务跑两次，对比两次的轨迹差异
    - 用途：定位不稳定的原因——是模型随机性、工具波动，还是环境差异
    - 价值：把「偶发失败」变成「可复现问题」
  - 工具调用 Mock
    - 调试时用 Mock 替代真实工具调用
    - 用途：避免副作用（发邮件、删数据）、加速调试、构造边界场景
    - 价值：让调试可重复、可控、无副作用
- 工具生态
  - LangSmith：LangChain 生态的调试与追踪平台
  - LangFuse：开源可观测性平台，支持轨迹回放
  - 其他：AgentOps、Phoenix（Arize）
- 工程价值
  - 没有调试基础设施，Agent 的 Bad Case 只能靠猜
  - 有了调试基础设施，Bad Case 可以像传统软件一样断点调试
  - 这是 Agent 从「能用」到「可维护」的关键基础设施

## 十、成本与性能工程

- 成本控制
  - 循环步数控制：硬性上限，避免无限循环
  - 模型路由：简单步骤用小模型，复杂决策用大模型
  - 工具结果缓存：相同工具调用复用结果
  - 上下文压缩：减少每步的 token 消耗
  - 按需规划：简单任务不做完整规划
- 性能优化
  - 工具调用并行化：无依赖的工具调用并行执行（呼应 3.1 DAG 依赖图）
  - 流式输出：让用户看到 Agent 的思考过程
  - 异步执行：长任务异步处理，不阻塞用户
  - 预取：预测下一步可能用到的工具，提前准备
- 延迟拆解
  - 规划耗时
  - 工具选择耗时
  - 工具执行耗时
  - 反思耗时
  - LLM 生成耗时
  - 网络与排队

## 十二、落地工程难点

- 工具描述质量（地基瓶颈）：工具描述写不好，Agent 就选不对工具
- 循环控制（效果天花板）：何时停止、如何避免死循环，是 Agent 最难的部分
- 错误恢复：工具失败、结果不符预期时，Agent 能否自我修正
- 安全与权限：Agent 有行动能力，权限控制比 RAG 更关键
- 成本与延迟：多轮循环导致成本和延迟远高于单次 LLM 调用
- 评估体系：Agent 的轨迹评估比 RAG 的答案评估更复杂
- 调试基础设施：没有轨迹回放和中间状态注入，Bad Case 只能靠猜
- 核心认知：Demo 几小时，调到生产可用需要数周到数月

### 12.1 Agent 常见反模式

- 工具描述模糊导致选错工具
  - 表现：工具描述只写「查询数据」，没写查什么数据、什么时候用
  - 后果：Agent 在多个相似工具之间随机选择
  - 正解：工具描述要说清「什么时候用、什么时候不用、返回什么」
- 没有硬性终止条件
  - 表现：只靠 LLM 判断「任务完成」，没有步数/时间上限
  - 后果：Agent 陷入死循环，消耗大量 token
  - 正解：必须设置硬性上限（步数、时间、成本），LLM 判断只是辅助
- 把所有工具都塞进 Prompt
  - 表现：工具超过 20 个还全量注入
  - 后果：Prompt 过长，工具选择准确率下降
  - 正解：工具多时用检索式选择或分层路由
- 让 Agent 做工作流该做的事
  - 表现：流程完全固定的任务也用 Agent
  - 后果：不可控、难调试、成本高，还不如工作流稳定
  - 正解：能工作流解决的就不要用 Agent，复杂生产系统用 Agentic Workflow
- 不可逆操作没有确认机制
  - 表现：Agent 直接删数据、发邮件，没有人工确认
  - 后果：一次误判造成实际损失
  - 正解：不可逆操作必须在系统层强制人工确认
- 忽略工具返回内容的注入风险
  - 表现：只过滤用户输入，不过滤工具返回内容
  - 后果：网页/文档中的恶意指令被 Agent 执行
  - 正解：工具返回内容也必须做注入检测
- 反思没有硬性上限
  - 表现：让模型自由反思，不设最大次数
  - 后果：模型陷入「为改而改」的死循环
  - 正解：硬设 2~3 轮最大反思次数
- 任务复杂就上 Multi-Agent
  - 表现：任务一复杂就拆多 Agent，不做选型判断
  - 后果：复杂度飙升，效果反而不如单 Agent
  - 正解：只在单 Agent 上下文撑爆、跨领域分工、可并行子任务三种情况下才用 Multi-Agent
- 沙箱隔离级别一刀切
  - 表现：所有代码执行都用同一隔离级别，不区分风险
  - 后果：高风险操作隔离不足，低风险操作开销过大
  - 正解：按代码来源、操作类型、租户、合规要求分级选隔离级别
- 没有调试基础设施
  - 表现：Agent 出问题只能靠看日志猜，无法复现和定位
  - 后果：Bad Case 排查效率极低，无法系统性优化
  - 正解：引入轨迹回放、中间状态注入、对比调试等开发者调试能力
