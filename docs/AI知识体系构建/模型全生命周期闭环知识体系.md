# 模型全生命周期闭环知识体系

> 本体系是六个专题的**横向衔接层**；目录统一入口为[总索引](README.md)。
> 六份体系讲「每一层怎么做」，本体系只讲「层与层之间怎么连」。
> 不重复六份体系的技术细节，只写反馈、约束、需求的流动路径。
>
> 建议学习路径：
>
> 1. Prompt 工程完整知识体系    ← 基础工具，最先学（RAG、Agent 都依赖它）
> 2. RAG 完整知识体系          ← 主战场
> 3. Agent 完整知识体系         ← 主战场，紧接 RAG
> 4. 推理部署完整知识体系       ← 必备背景，和 2、3 并行
> 5. 模型全生命周期闭环         ← 衔接层，前四份学完再看
> 6. LLM 训练完整知识体系       ← 背景知识，选读
> 7. 多模态训练完整知识体系     ← 加分项，按需



## 一、基础认知

- 核心定义
  - 全称：模型全生命周期闭环（Model Lifecycle Loop）
  - 核心解决：六个专题各自侧重不同层，但「层与层之间怎么连」没有说清楚
  - 本质：把「训练 → 推理 → 应用」串成一个可迭代的环，让每一层的输出成为下一层的输入
- 与六份体系的本质区别
  - 六份体系：纵向深入，解决「这一层怎么做」
  - 本体系：横向衔接，解决「层与层之间怎么连」
  - 读者定位：应用路线先了解 Prompt/RAG/Agent/部署；训练闭环再补训练与多模态，不要求人人先读完全部六卷
- 解决的三大核心问题
  - 反馈回流：线上 bad case 如何转化为训练数据
  - 约束反向传导：推理侧的延迟/成本约束如何反向影响训练决策
  - 需求回流：应用层的新需求如何驱动模型层的能力升级
- 核心价值
  - 闭环迭代：不是一次性交付，而是持续优化的系统
  - 全链路优化：不只看单层指标，看端到端效果
  - 成本可控：把「用户纠正」转化为「模型改进」，减少人工介入

## 二、闭环全景图

- 五个环节
  - 训练层：LLM 训练 + 多模态训练
  - 推理层：推理部署
  - 应用层：RAG + Agent
  - 反馈层：用户反馈、bad case 收集、自动评估
  - 回流层：数据回流、约束回流、需求回流
- 闭环的三个方向
  - 向前：训练 → 推理 → 应用（能力传递）
  - 向后：应用 → 反馈 → 训练（反馈回流）
  - 横向：推理约束 ↔ 训练决策（约束反向传导）
- 关键认知
  - 闭环不是自动的，需要工程系统支撑
  - 闭环的价值在于「缩短迭代周期」
  - 不是所有反馈都值得回流，需要筛选

## 三、反馈回流（应用层 → 训练层）

### 3.1 反馈来源

- 显式反馈
  - 点赞/点踩
  - 评分
  - 追问
  - 转人工
- 隐式反馈
  - 会话时长
  - 复制行为
  - 重试行为
  - 放弃行为
- 系统反馈
  - Bad case 日志
  - 幻觉检测告警
  - 检索失败记录
  - Agent 任务失败记录

### 3.2 反馈筛选

- 核心问题：不是所有反馈都值得回流，噪声反馈会污染训练数据
- 筛选维度
  - 置信度：反馈是否明确（点赞明确，会话时长短不一定）
  - 代表性：是否代表一类问题，还是个案
  - 可转化性：能否转化为训练数据（有些反馈无法转化为 SFT/偏好数据）
- 筛选方法
  - 规则过滤：明显噪声直接过滤
  - 模型过滤：用小模型判断反馈质量
  - 人工抽检：关键反馈人工确认

### 3.3 反馈转化

- 转化为 SFT 数据
  - 适用：用户明确纠正了错误答案
  - 转化方式：用户问题 + 正确回答 → SFT 样本
  - 注意：用户纠正不一定正确，需要校验
- 转化为偏好数据
  - 适用：用户对多个回答有明确偏好
  - 转化方式：prompt + chosen + rejected → 偏好对
  - 注意：偏好数据需要成对，单个反馈难以转化
- 转化为 RAG 知识
  - 适用：知识库缺失导致回答错误
  - 转化方式：把缺失内容补充进知识库
  - 注意：不是所有错误都靠训练解决，有些靠补知识库
- 转化为 Agent 工具
  - 适用：Agent 无法完成的任务
  - 转化方式：把缺失能力封装成新工具
  - 注意：工具设计要遵循 Agent 卷的工具设计原则
- 转化为 Prompt
  - 适用：bad case 是「表述/约束没说清」，而非模型能力不足
  - 转化方式：把纠正固化进 Prompt 模板、角色设定或 few-shot 示例
  - 优势：改动最快、可灰度、可回滚，不需要动训练
  - 注意：Prompt 是**反馈回流的最小单元**，但不是万能——能力性缺陷仍要回流到训练层

### 3.4 反馈回流的工程系统

- 数据管道
  - 反馈收集 → 核实/归因 → 选择 Prompt/索引/工具/服务/模型改动 → 评测 → 发布
- 版本管理
  - 每次回流的反馈要记录来源、转化方式、影响范围
- 效果验证
  - 回流后的模型要评估，确认是否真的改进
  - A/B 测试：新旧模型对比
- 常见问题
  - 反馈噪声：未经筛选直接回流，污染数据
  - 回流延迟：反馈到训练周期太长，失去时效性
  - 效果不验证：回流后不评估，不知道有没有用

## 四、约束反向传导（推理层 ↔ 训练层）

### 4.1 推理约束对训练的影响

- 延迟约束
  - 推理延迟要求 → 模型大小选择
  - 例：端侧按内存、功耗、时延和任务选择模型/量化，不设统一 7B 上限
  - 例：实时对话要求低延迟 → 训练侧优化推理效率
- 成本约束
  - 推理成本要求 → 参数量/量化策略
  - 例：成本受激活计算、KV、硬件、负载与调度影响 → 联合比较模型、数据与服务方案
- 量化约束
  - 推理量化要求 → 训练侧考虑量化友好性
  - 例：要跑 INT4 推理 → 训练侧要评估量化后的精度损失
- 部署约束
  - 部署环境要求 → 训练侧选择架构
  - 例：国产芯片部署 → 训练侧适配昇腾等生态

### 4.2 训练决策对推理的反向影响

- 模型架构决定推理效率
  - MoE：总参数大、激活参数小 → 推理显存大但计算量小
  - GQA：减少 KV Cache → 推理显存降低
  - 量化友好架构：训练时就考虑量化，推理时精度损失小
- 训练数据决定推理质量
  - 训练数据分布 → 推理时的泛化能力
  - 训练数据的领域覆盖 → 推理时的领域适配
- 对齐策略决定推理行为
  - RLHF 对齐 → 推理时的安全行为
  - 拒绝策略 → 推理时的拒答行为

### 4.3 约束反向传导的工程实践

- 训练侧要了解推理约束
  - 训练团队要知道模型的部署环境
  - 训练目标要包含推理效率
- 推理侧要反馈实际问题
  - 推理团队要把实际遇到的瓶颈反馈给训练团队
  - 例：某类 query 延迟高 → 训练侧优化相关能力
- 联合优化
  - 不是训练完再考虑推理，而是训练时就考虑推理
  - 例：训练时评估量化后的精度

## 五、需求回流（应用层 → 训练层）

### 5.1 应用需求驱动能力升级

- 新任务需求
  - 新任务 → 评估已有模型/工具适配，再决定是否训练
  - 例：代码需求 → 比较已有代码模型、工具验证与微调方案
- 新领域需求
  - 新领域 → 判断是动态知识接入、业务工具还是模型能力缺口
  - 例：高风险领域 → 先定义专家审核、数据授权与安全门禁，不默认训练即可解决
- 新模态需求
  - 新模态 → 比较现成多模态模型、预处理与训练方案
  - 例：用户上传图片 → 选择兼容视觉模型和安全输入处理，按需训练

### 5.2 需求回流的工程实践

- 需求收集
  - 从应用层收集需求，不是拍脑袋
  - 数据驱动：用真实用户 query 分布驱动
- 需求优先级
  - 不是所有需求都值得做
  - 按频次、影响、成本排序
- 需求转化
  - 需求 → 归因/预算 → Prompt、索引、工具、服务或模型方案 → 验证
  - 每个环节都要可追溯

## 六、闭环的工程系统

### 6.1 数据基础设施

- 数据收集
  - 应用层的 query、反馈、bad case
  - 推理层的延迟、成本、错误
  - 训练层的实验、指标、版本
- 数据存储
  - 统一的数据湖，避免数据孤岛
  - 元数据管理：来源、版本、用途
- 数据处理
  - 筛选、转化、去重、质量过滤

### 6.2 实验系统

- A/B 测试
  - 新旧模型对比
  - 新旧策略对比
- 灰度发布
  - 逐步放量，发现问题及时回滚
- 效果归因
  - 改动和效果的因果关系

### 6.3 监控系统

- 端到端监控
  - 从训练到推理到应用的全链路监控
- 关键指标
  - 训练层：loss、评估指标
  - 推理层：延迟、吞吐、成本
  - 应用层：任务完成率、用户满意度
- 告警
  - 异常自动告警
  - Bad case 自动收集

### 6.4 迭代流程

- 标准迭代流程
  - 收集反馈 → 核实/归因 → 最小有效改动 → 离线评测 → 灰度发布 → 监控/回滚
- 迭代周期
  - 轻量迭代：Prompt、解析、索引或工具；周期取决于验证与审核
  - 模型适配：SFT/LoRA/偏好优化；周期受数据、算力与风险评测影响
  - 大规模训练：资源与研究成本通常更高，不给固定交付周期
- 版本管理
  - 每个版本可追溯
  - 支持回滚

### 6.5 版本契约与发布证据

- 数据：来源/授权、集合划分、清洗/标注规则、快照、删除和 ACL 状态。
- 模型：权重、tokenizer、processor、adapter、量化配置、引擎与解码参数。
- 应用：Prompt/schema、embedding、切片/索引活动版本、工具契约、权限策略。
- 实验：代码提交、依赖、seed、预算、基线/消融、质量与安全结果、负载和失败记录。
- 发布：把兼容版本组合成 release manifest，禁止新 embedding 读旧空间、新 processor 配旧模型。离线门禁后灰度，设置停止/回滚责任人和指标。
- 回滚：恢复兼容组合，核对外部副作用；权限撤销、法规要求删除与已发生动作不能通过恢复旧快照撤销。
- 反馈：用户纠正与点赞不等于事实标签；审核后进入开发/训练集，最终留出集独立维护。

应用不改模型时，也要记录 Prompt、索引、工具和策略变化。评测合同见[评测方法](评测与实验方法.md)，演练见[实践清单](实践与验收清单.md)。

## 七、闭环的常见反模式

- 反馈不筛选直接回流
  - 表现：所有用户反馈都进训练数据
  - 后果：噪声污染训练数据
  - 正解：筛选后再回流
- 回流后不验证
  - 表现：回流后不评估，不知道有没有用
  - 后果：可能越改越差
  - 正解：A/B 测试验证效果
- 训练侧不了解推理约束
  - 表现：训练完才发现推理跑不动
  - 后果：返工
  - 正解：训练时就考虑推理约束
- 应用需求不驱动训练
  - 表现：训练侧按自己的节奏做，不管应用需求
  - 后果：训练出来的能力用不上
  - 正解：用真实用户 query 分布驱动训练
- 闭环周期太长
  - 表现：反馈到训练到发布，几个月
  - 后果：反馈失效，用户流失
  - 正解：缩短迭代周期，分级迭代
- 只做单向闭环
  - 表现：只做反馈回流，不做约束反向传导
  - 后果：训练和推理脱节
  - 正解：双向闭环
- 没有数据基础设施
  - 表现：数据散落各处，无法统一处理
  - 后果：闭环跑不起来
  - 正解：先建数据基础设施

## 八、闭环的价值衡量

- 迭代速度
  - 从反馈到改进的时间
  - 在质量、安全与审核门禁满足后优化周期，不盲目追求越短越好
- 反馈转化率
  - 经核实反馈中，有多少被有效处理（Prompt、知识、工具、服务或模型改动）
  - 转化率不能单独证明改进；需看证据、任务成功、误拒、安全与成本
- 改进有效率
  - 回流后真正改进的比例
  - 有效率低说明筛选或转化有问题
- 端到端效果
  - 用户满意度、任务完成率
  - 最终衡量标准
- 成本节约
  - 通过闭环减少的人工介入
  - 例：减少转人工率

## 九、与六份体系的关系

| 六份体系                | 解决什么               | 闭环体系接什么                       |
| ----------------------- | ---------------------- | ------------------------------------ |
| Prompt 工程完整知识体系 | 人机指令与上下文控制 | bad case → 改 Prompt（最小回流单元） |
| RAG 完整知识体系        | 模型知识陈旧/私有知识  | RAG 失败 → 分析解析、索引、权限、检索与生成    |
| Agent 完整知识体系      | 模型行动力/工具调用    | Agent 任务失败 → 加工具 or 改基座    |
| LLM 训练完整知识体系    | 纯文本基座与对齐       | 接收反馈数据、约束传导               |
| 多模态训练完整知识体系  | 视觉/多模态感知        | 接收多模态 bad case                  |
| 推理部署完整知识体系    | 模型服务化与成本       | 输出延迟/成本约束给训练侧            |

- 闭环体系不做技术纵深，只做衔接
- 六份体系各自独立，闭环体系把它们串起来
- 按[岗位路线](ai_study_route.md)学习；训练/多模态相关环节按需补读
- **Prompt 在闭环中的特殊角色**：它是所有回流路径里**粒度最小、见效最快**的一环
  - 线上 bad case 先归因；选择有效且成本可控的改动，不把 Prompt 设为一切问题的必经步骤
  - Prompt 改动可灰度、可回滚，是 A/B 实验成本最低的对象
  - Prompt 路由本身承担「需求分流」：不同 query 类型走不同 Prompt / 不同模型
  - 知识缺失、工具/权限、服务或模型能力问题直接进入对应路径；无需先用 Prompt 修一遍
