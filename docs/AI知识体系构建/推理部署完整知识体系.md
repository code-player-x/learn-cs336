# 推理部署完整知识体系

> 本版本在上一版基础上，补入 PD 分离、国产芯片推理生态、QAT 占位、多模态推理视觉预处理一致性四条。新增内容以 **【定稿】** 标记。

## 一、推理部署基础认知

- 核心定义
  - 全称：大语言模型推理部署（LLM Inference & Deployment）
  - 核心解决：把训练好的模型权重变成可对外服务的在线系统
  - 本质：在给定硬件和延迟/成本约束下，最大化推理吞吐和质量
- 与训练的本质区别
  - 训练：前向 + 反向 + 参数更新，吞吐导向，离线批处理
  - 推理：只做前向传播，延迟导向，在线实时响应
  - 核心差异：训练优化「单位时间处理多少 token」，推理优化「单位请求多快返回 + 单位成本能服务多少请求」
- 推理的两个阶段
  - Prefill（预填充）：处理输入 prompt，计算 KV Cache，是计算密集型
  - Decode（解码）：逐 token 生成，每步只处理一个 token，是访存密集型
  - 两阶段特性不同，优化手段不同
  - 两个阶段的物理特性差异，直接催生了 PD 分离架构 【定稿】
- 核心指标
  - TTFT（Time To First Token）：首 token 延迟，反映 prefill 速度
  - TPOT（Time Per Output Token）：每 token 生成时间，反映 decode 速度
  - 吞吐（Throughput）：单位时间处理的请求数或 token 数
  - 延迟（Latency）：端到端响应时间
  - 成本（Cost）：单位 token 的算力成本
- 核心矛盾
  - 延迟 vs 吞吐：批处理提升吞吐但增加延迟
  - 质量 vs 成本：大模型质量好但成本高
  - 显存 vs 并发：KV Cache 占显存，显存限制并发数
  - Prefill vs Decode：两阶段特性不同，混跑会互相干扰 【定稿】

## 二、推理部署完整工作流程

- 模型准备
  - 权重加载：从 checkpoint 加载模型权重
  - 量化：将 FP16/BF16 权重转为 INT8/INT4/FP8
  - 图优化：算子融合、CUDA Graph 捕获
- 服务启动
  - 加载模型到 GPU
  - 初始化 KV Cache 池
  - 启动调度器
  - 如果是 PD 分离架构，Prefill 和 Decode 分别启动 【定稿】
- 请求处理
  - 请求到达 → 排队 → 调度 → prefill → decode → 流式返回
  - Continuous Batching：动态组批，请求完成即退出，新请求即加入
  - 调度策略：FCFS、优先级、SJF（短作业优先）
  - PD 分离架构下：请求先到 Prefill 集群，KV Cache 传给 Decode 集群 【定稿】
- 输出返回
  - 流式输出：逐 token 返回，降低感知延迟
  - 后处理：停止条件判断、内容过滤
- 监控与扩缩容
  - 实时监控：TTFT、TPOT、吞吐、显存
  - 自动扩缩容：按负载动态增减实例

## 三、核心组件详解

### 3.1 推理引擎

- vLLM
  - 核心创新：PagedAttention，把 KV Cache 分页管理
  - 优势：显存利用率高，吞吐大
  - 适用：通用 LLM 推理，社区活跃
- TensorRT-LLM
  - 核心：NVIDIA 官方推理框架，深度优化
  - 优势：极致性能，支持 FP8/INT4
  - 劣势：编译复杂，绑定 NVIDIA 生态
  - 适用：生产环境，追求极致性能
- SGLang
  - 核心：RadixAttention，前缀共享
  - 优势：多轮对话场景性能好
  - 适用：对话系统、Agent
- TGI（Text Generation Inference）
  - HuggingFace 官方推理框架
  - 优势：易用，与 HF 生态集成
  - 适用：快速原型
- llama.cpp
  - 核心：CPU/GPU 混合推理，支持 GGUF 格式
  - 优势：消费级硬件可跑
  - 适用：端侧、个人部署
- Ollama
  - 核心：llama.cpp 的封装，一键部署
  - 优势：极简
  - 适用：本地开发、个人使用
- **【定稿】非 NVIDIA 生态推理栈**
  - **昇腾 NPU**
    - MindIE：华为官方推理引擎，支持昇腾芯片
    - vLLM-ascend：vLLM 的昇腾适配版
    - 适用：国产化信创场景
  - **AMD ROCm**
    - ROCm + vLLM：AMD GPU 的推理方案
    - 适用：非 NVIDIA GPU 场景
  - **海光 DCU / 燧原等国产芯片**
    - 各家有自己的推理栈，生态仍在完善
    - 工程要点：国产化落地要提前评估适配
- 选型维度
  - 硬件：NVIDIA、AMD、国产芯片
  - 场景：在线服务、离线批处理、端侧
  - 性能要求：延迟优先、吞吐优先
  - 生态：社区活跃度、文档质量
  - 合规：是否需要国产化信创

### 3.2 KV Cache 管理

- 核心问题
  - KV Cache 占显存，随序列长度线性增长
  - 显存限制并发数，是推理的核心瓶颈
- PagedAttention（vLLM 核心创新）
  - 核心：把 KV Cache 分成固定大小的 block，按需分配
  - 优势：显存碎片少，利用率高
  - 效果：吞吐提升 2-4 倍
- Prefix Caching
  - 核心：相同前缀的请求共享 KV Cache
  - 适用：多轮对话、少样本提示、系统提示
  - 效果：显著降低重复计算
- RadixAttention（SGLang）
  - 核心：用 radix tree 管理前缀，自动共享
  - 优势：比 Prefix Caching 更灵活
- KV Cache 量化
  - 核心：把 KV Cache 从 FP16 量化到 INT8/FP8
  - 效果：显存降低 50%，精度损失小
- KV Cache 淘汰策略
  - 核心：显存不足时淘汰部分 KV
  - 方法：LRU、H2O、StreamingLLM
  - 权衡：淘汰后需要重新计算，增加延迟
- KV Cache 传输（PD 分离架构下）【定稿】
  - 核心：Prefill 算完的 KV Cache 要传给 Decode 集群
  - 方式：网络传输（RDMA、NVLink）
  - 挑战：传输延迟、带宽、序列化开销
  - 代表：Mooncake 架构

### 3.3 量化

- 量化基础
  - 核心：把高精度权重/激活转为低精度
  - 目标：降低显存、加速推理
  - 权衡：精度损失 vs 性能提升
- 权重量化
  - GPTQ：训练后量化，逐层量化，精度好
  - AWQ：激活感知量化，保护重要权重
  - GGUF：llama.cpp 格式，支持多种量化级别
  - bitsandbytes：HuggingFace 集成，易用
- 激活量化
  - SmoothQuant：平滑激活异常值，使激活可量化
  - FP8：Hopper/Blackwell 原生支持，精度和性能平衡
- KV Cache 量化
  - 核心：KV Cache 也量化，进一步降显存
  - 方法：INT8、FP8
- 量化级别对比
  - FP16/BF16：无量化，精度最高，显存最大
  - FP8：精度接近 FP16，显存降低 50%
  - INT8：精度略降，显存降低 50%
  - INT4：精度明显下降，显存降低 75%
- **【定稿】QAT（量化感知训练）作为兜底**
  - 核心：当 PTQ 精度掉得太厉害时，退回训练侧用 QAT
  - 机制：在训练/微调阶段就模拟量化误差，让模型适应低精度
  - 与 PTQ 的关系
    - PTQ：训练后量化，成本低，精度有损
    - QAT：训练时量化，成本高，精度损失小
  - 工程要点
    - 先试 PTQ，精度不够再退回 QAT
    - QAT 属于训练侧，详见《LLM 训练完整知识体系》
- 工程要点
  - 量化后必须评估精度损失
  - 不同任务对量化敏感度不同
  - 量化不是万能的，有些模型量化后效果崩

### 3.4 批处理与调度

- 静态批处理
  - 核心：一次处理固定数量的请求
  - 问题：请求长度不同，短请求等长请求，效率低
- Continuous Batching（连续批处理）
  - 核心：动态组批，请求完成即退出，新请求即加入
  - 优势：吞吐大幅提升，延迟可控
  - 采用者：vLLM、TensorRT-LLM、TGI
- 调度策略
  - FCFS：先到先服务，公平但可能长请求阻塞
  - 优先级：高优先级先处理
  - SJF：短作业优先，降低平均延迟
  - 公平调度：避免饥饿
- Chunked Prefill
  - 核心：长 prompt 分块 prefill，避免阻塞 decode
  - 优势：降低 TTFT 抖动，提升整体吞吐
- Speculative Decoding（投机解码）
  - 核心：用小模型草拟多个 token，大模型验证
  - 优势：加速 decode，2-3 倍提速
  - 变体：Medusa、EAGLE、Lookahead
  - 适用：decode 是瓶颈的场景

### 3.5 推理优化

- 算子融合
  - 核心：把多个算子合并为一个，减少 kernel launch 开销
  - 常见：LayerNorm + Linear、Attention 融合
- CUDA Graph
  - 核心：把整个推理图捕获为静态图，减少 launch 开销
  - 适用：decode 阶段，固定 shape
- FlashAttention（推理版）
  - 核心：分块计算 + 在线 softmax，降低显存
  - 推理优势：支持长上下文
- FlashDecoding
  - 核心：decode 阶段并行化，加速长序列 decode
- 分页注意力（PagedAttention）
  - 见 3.2 KV Cache 管理
- 张量并行推理
  - 核心：模型切分到多卡，并行推理
  - 适用：单卡放不下的大模型
- 流水线并行推理
  - 核心：模型分层切分，流水线执行
  - 适用：超大模型
- 专家并行推理（MoE）
  - 核心：不同专家分布在不同卡上
  - 挑战：All-to-All 通信

### 3.6 服务化

- API 网关
  - 职责：鉴权、限流、路由、日志
  - 常见：Nginx、Kong、APISIX
- 限流
  - 核心：防止过载
  - 策略：令牌桶、漏桶、滑动窗口
- 降级
  - 核心：过载时降级服务
  - 策略：小模型替代、缓存命中、拒绝新请求
- 负载均衡
  - 核心：请求分发到多实例
  - 策略：轮询、最少连接、一致性哈希
- 多实例部署
  - 核心：多个推理实例，水平扩展
  - 挑战：模型加载、显存管理、版本一致性

### 3.7 分布式推理与架构

- 张量并行（TP）
  - 核心：层内切分，每卡算一部分
  - 通信：每层 all-reduce
  - 适用：单卡放不下的大模型
- 流水线并行（PP）
  - 核心：层间切分，不同卡算不同层
  - 通信：层间传递激活
  - 适用：超大模型
- 专家并行（EP）
  - 核心：MoE 专家分布到不同卡
  - 通信：All-to-All
  - 挑战：负载均衡、通信开销
- 混合并行
  - 核心：组合 TP + PP + EP
  - 适用：超大模型 + 多卡部署
- 多实例并行
  - 核心：多个独立实例，水平扩展
  - 适用：模型能单卡放下时
- **【定稿】PD 分离（Prefill-Decode Disaggregation）**
  - 核心问题：Prefill 和 Decode 混跑互相干扰
    - Prefill 是计算密集型，占用大量算力
    - Decode 是访存密集型，需要持续低延迟
    - 混跑时，长 prompt 的 Prefill 阻塞 Decode，导致 TPOT 抖动
  - 核心思想：把 Prefill 和 Decode 拆到不同的 GPU 集群
    - Prefill 集群：大算力卡，处理输入
    - Decode 集群：高显存带宽卡，逐 token 生成
    - 中间通过 KV Cache 传输连接
  - 代表架构
    - **Mooncake**：月之暗面的分离式架构
    - **vLLM V1**：vLLM 的 PD 分离实现
    - **字节、阿里等大厂**：自研 PD 分离架构
  - 优势
    - Prefill 和 Decode 各自优化，互不干扰
    - 资源利用率更高，成本更低
    - 长上下文场景 TPOT 更稳定
  - 挑战
    - KV Cache 传输：网络带宽、延迟、序列化开销
    - 调度复杂度：两个集群的协调
    - 故障处理：任一集群故障都影响整体
  - 与 Chunked Prefill 的关系
    - Chunked Prefill：软件解法，把长 prefill 分块，减少阻塞
    - PD 分离：架构解法，物理隔离两个阶段
    - 两者可以组合使用

## 四、推理 vs 训练

- 本质区别
  - 训练：前向 + 反向 + 参数更新，吞吐导向
  - 推理：只做前向传播，延迟导向
- 优化目标不同
  - 训练优化：单位时间处理多少 token
  - 推理优化：单位请求多快返回 + 单位成本服务多少请求
- 硬件需求不同
  - 训练：大显存、高带宽、多卡互联
  - 推理：低延迟、高并发、成本敏感
- 技术栈不同
  - 训练：PyTorch、DeepSpeed、Megatron
  - 推理：vLLM、TensorRT-LLM、SGLang
- 选型判断
  - 训练完的模型 → 推理部署
  - 推理约束 → 反向影响训练决策（见闭环体系）

## 五、高级推理范式

- Speculative Decoding
  - 核心：小模型草拟 + 大模型验证
  - 变体：Medusa、EAGLE、Lookahead
- Multi-Token Prediction
  - 核心：一次预测多个 token
  - 代表：Medusa
- 树状解码
  - 核心：并行探索多个候选路径
  - 代表：Tree of Thoughts 推理版
- 推理时计算扩展
  - 核心：推理时增加计算量提升质量
  - 代表：o1 风格的思维链推理
  - 权衡：质量提升 vs 延迟/成本增加
- 结构化输出
  - 核心：约束输出格式（JSON、XML）
  - 方法：Grammar-based decoding、JSON mode
- 多模态推理
  - 核心：图文混合推理
  - 挑战：视觉 token 计算、模态对齐
  - **【定稿】视觉预处理一致性**
    - 核心问题：推理引擎的图像预处理 pipeline 必须与训练 recipe 严格对齐
    - 训练侧 resize：按训练 recipe 做 resize
    - 推理侧 resize：按推理引擎默认做 resize
    - 不一致的后果：视觉 token 错位 → logprob 偏差 → 输出异常
    - 工程要点
      - 插值方法、目标尺寸、padding 策略都要对齐
      - 推理引擎的图像预处理要按训练 recipe 配置，不能用默认
      - 这是多模态训练卷和推理卷的跨卷接缝

## 十一、落地工程难点

- 显存瓶颈：KV Cache 占显存，限制并发
- 延迟优化：TTFT 和 TPOT 都难优化
- 成本控制：GPU 成本高，利用率难提升
- 量化精度：量化后精度损失难控制
- 批处理效率：请求长度差异大，批处理效率低
- 多实例一致性：多实例部署，版本一致性难保证
- 国产芯片适配：昇腾等生态不完善
- 长上下文推理：长上下文 KV Cache 爆炸
- MoE 推理：专家并行通信开销大
- PD 分离工程：KV Cache 传输、调度协调、故障处理 【定稿】
- 多模态推理预处理：训练和推理 resize 不一致 【定稿】
- 核心认知：推理部署是「工程密集型」，不是「算法密集型」，工程细节决定成败

### 11.1 推理部署常见反模式

- 不做量化直接部署
  - 表现：FP16 直接部署，显存不够
  - 后果：并发低，成本高
  - 正解：按场景选择量化级别
- 量化后不评估精度
  - 表现：量化后直接上线，不测效果
  - 后果：精度崩了不知道
  - 正解：量化后必须评估精度损失，PTQ 不行退回 QAT
- 不用 Continuous Batching
  - 表现：静态批处理，短请求等长请求
  - 后果：吞吐低，延迟高
  - 正解：用 Continuous Batching
- 忽略 KV Cache 管理
  - 表现：KV Cache 不做分页、不做前缀共享
  - 后果：显存浪费，并发低
  - 正解：PagedAttention + Prefix Caching
- 单实例部署
  - 表现：只部署一个实例
  - 后果：单点故障，无法扩展
  - 正解：多实例 + 负载均衡
- 不做限流降级
  - 表现：没有限流，过载直接崩
  - 后果：雪崩
  - 正解：限流 + 降级 + 熔断
- 不监控关键指标
  - 表现：只看 QPS，不看 TTFT/TPOT
  - 后果：用户体验差不知道
  - 正解：全链路监控
- 长上下文不做优化
  - 表现：长上下文直接推理，KV Cache 爆炸
  - 后果：无法支持长上下文
  - 正解：KV Cache 量化 + 淘汰策略 + FlashDecoding
- MoE 不做专家并行
  - 表现：MoE 模型单卡部署
  - 后果：显存不够
  - 正解：专家并行 + All-to-All 优化
- 忽略国产芯片适配
  - 表现：只考虑 NVIDIA，不考虑国产芯片
  - 后果：国产化要求时无法落地
  - 正解：提前评估国产芯片适配
- **【定稿】长上下文混跑不做 PD 分离**
  - 表现：Prefill 和 Decode 混跑，长 prompt 阻塞 decode
  - 后果：TPOT 抖动，长上下文体验差
  - 正解：Chunked Prefill 或 PD 分离架构
- **【定稿】多模态推理不做视觉预处理一致性校验**
  - 表现：训练侧和推理侧 resize 不一致
  - 后果：视觉 token 错位，输出异常
  - 正解：推理引擎的图像预处理 pipeline 必须与训练 recipe 严格对齐
