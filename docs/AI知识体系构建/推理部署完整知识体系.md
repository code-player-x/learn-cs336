# 推理部署完整知识体系

> 本卷覆盖模型服务、容量、量化与负载验收。工具名称是技术实例，不是性能排名或长期选型承诺；返回[总索引](README.md)，实验口径见[评测方法](评测与实验方法.md)。

## 一、推理部署基础认知

- 核心定义
  - 全称：大语言模型推理部署（LLM Inference & Deployment）
  - 核心解决：把训练好的模型权重变成可对外服务的在线系统
  - 本质：在给定硬件和延迟/成本约束下，最大化推理吞吐和质量
- 与训练的本质区别
  - 训练：前向 + 反向 + 参数更新，吞吐导向，离线批处理
  - 推理：只做前向传播，延迟导向，在线实时响应
  - 核心差异：训练优化「单位时间处理多少 token」，推理优化「单位请求多快返回 + 单位成本能服务多少请求」
- 推理的两个阶段
  - Prefill（预填充）：处理输入 prompt，计算 KV Cache，是计算密集型
  - Decode（解码）：逐 token 生成，每步只处理一个 token，是访存密集型
  - 两阶段特性不同，优化手段不同
  - 两个阶段的物理特性差异，直接催生了 PD 分离架构 【定稿】
- 核心指标
  - TTFT（Time To First Token）：首 token 延迟，反映 prefill 速度
  - TPOT（Time Per Output Token）：每 token 生成时间，反映 decode 速度
  - 吞吐（Throughput）：单位时间处理的请求数或 token 数
  - 延迟（Latency）：端到端响应时间
  - 成本（Cost）：单位 token 的算力成本
- 核心矛盾
  - 延迟 vs 吞吐：批处理提升吞吐但增加延迟
  - 质量 vs 成本：大模型质量好但成本高
  - 显存 vs 并发：KV Cache 占显存，显存限制并发数
  - Prefill vs Decode：两阶段特性不同，混跑会互相干扰 【定稿】

## 二、推理部署完整工作流程

- 模型准备
  - 权重加载：从 checkpoint 加载模型权重
  - 量化：将 FP16/BF16 权重转为 INT8/INT4/FP8
  - 图优化：算子融合、CUDA Graph 捕获
- 服务启动
  - 加载模型到 GPU
  - 初始化 KV Cache 池
  - 启动调度器
  - 如果是 PD 分离架构，Prefill 和 Decode 分别启动 【定稿】
- 请求处理
  - 请求到达 → 排队 → 调度 → prefill → decode → 流式返回
  - Continuous Batching：动态组批，请求完成即退出，新请求即加入
  - 调度策略：FCFS、优先级、SJF（短作业优先）
  - PD 分离架构下：请求先到 Prefill 集群，KV Cache 传给 Decode 集群 【定稿】
- 输出返回
  - 流式输出：逐 token 返回，降低感知延迟
  - 后处理：停止条件判断、内容过滤
- 监控与扩缩容
  - 实时监控：TTFT、TPOT、吞吐、显存
  - 自动扩缩容：按负载动态增减实例

## 三、核心组件详解

### 3.1 推理引擎

- vLLM
  - 核心创新：PagedAttention，把 KV Cache 分页管理
  - 优势：显存利用率高，吞吐大
  - 适用：通用 LLM 推理，社区活跃
- TensorRT-LLM
  - 核心：NVIDIA 官方推理框架，深度优化
  - 特点：面向 NVIDIA 硬件的优化与量化内核；FP8/INT4 等支持依模型、硬件与实际版本核对
  - 劣势：编译复杂，绑定 NVIDIA 生态
  - 适用：具备相应硬件、模型兼容性与构建维护能力的场景；是否更快需同负载比较
- SGLang
  - 核心：RadixAttention，前缀共享
  - 优势：多轮对话场景性能好
  - 适用：对话系统、Agent
- TGI（Text Generation Inference）
  - HuggingFace 官方推理框架
  - 状态：截至 2026-09-27 官方已宣布进入 maintenance mode，接受小型修复、文档与轻量维护；见[官方说明](https://huggingface.co/docs/text-generation-inference/en/index)
  - 适用：已有 TGI 系统的维护或历史实现学习；新项目需比较活跃维护的兼容引擎，不把 TGI 列为默认原型推荐
- llama.cpp
  - 核心：CPU/GPU 混合推理，支持 GGUF 格式
  - 优势：消费级硬件可跑
  - 适用：端侧、个人部署
- Ollama
  - 核心：llama.cpp 的封装，一键部署
  - 优势：极简
  - 适用：本地开发、个人使用
- **【定稿】非 NVIDIA 生态推理栈**
  - **昇腾 NPU**
    - MindIE：华为官方推理引擎，支持昇腾芯片
    - vLLM-ascend：vLLM 的昇腾适配版
    - 适用：国产化信创场景
  - **AMD ROCm**
    - ROCm + vLLM：AMD GPU 的推理方案
    - 适用：非 NVIDIA GPU 场景
  - **海光 DCU / 燧原等国产芯片**
    - 各家有自己的推理栈，生态仍在完善
    - 工程要点：国产化落地要提前评估适配
- 选型维度
  - 硬件：NVIDIA、AMD、国产芯片
  - 场景：在线服务、离线批处理、端侧
  - 性能要求：延迟优先、吞吐优先
  - 生态：社区活跃度、文档质量
  - 合规：是否需要国产化信创

### 3.2 KV Cache 管理

- 核心问题
  - KV Cache 占显存，随序列长度线性增长
  - 显存限制并发数，是推理的核心瓶颈
- PagedAttention（vLLM 核心创新）
  - 核心：把 KV Cache 分成固定大小的 block，按需分配
  - 优势：显存碎片少，利用率高
  - 效果：降低 KV 内存浪费，吞吐收益需注明原论文/实验的基线、模型与负载，不保证固定倍数
- Prefix Caching
  - 核心：相同前缀的请求共享 KV Cache
  - 适用：多轮对话、少样本提示、系统提示
  - 效果：显著降低重复计算
- RadixAttention（SGLang）
  - 核心：用 radix tree 管理前缀，自动共享
  - 优势：比 Prefix Caching 更灵活
- KV Cache 量化
  - 核心：把 KV Cache 从 FP16 量化到 INT8/FP8
  - 效果：被量化 KV 的元素存储可约减半（另有 scale/metadata）；总显存与精度变化需测量
- KV Cache 淘汰策略
  - 核心：显存不足时淘汰部分 KV
  - 方法：LRU 通常用于可复用前缀块；H2O/StreamingLLM 等是活跃序列近似保留策略，两者语义不同
  - 权衡：前缀淘汰可重计算保持原语义；近似丢弃活跃 KV 可能改变输出，必须做质量回归
- KV Cache 传输（PD 分离架构下）【定稿】
  - 核心：Prefill 算完的 KV Cache 要传给 Decode 集群
  - 方式：网络传输（RDMA、NVLink）
  - 挑战：传输延迟、带宽、序列化开销
  - 代表：Mooncake 架构

### 3.3 量化

- 量化基础
  - 核心：把高精度权重/激活转为低精度
  - 目标：降低显存、加速推理
  - 权衡：精度损失 vs 性能提升
- 权重量化
  - GPTQ：训练后量化，逐层量化，精度好
  - AWQ：激活感知量化，保护重要权重
  - GGUF：llama.cpp 格式，支持多种量化级别
  - bitsandbytes：HuggingFace 集成，易用
- 激活量化
  - SmoothQuant：平滑激活异常值，使激活可量化
  - FP8：Hopper/Blackwell 原生支持，精度和性能平衡
- KV Cache 量化
  - 核心：KV Cache 也量化，进一步降显存
  - 方法：INT8、FP8
- 量化级别对比
  - FP16/BF16：常见精度基线，不等于所有格式中精度最高
  - FP8：元素存储约为 16-bit 一半，质量依缩放/任务/内核验证
  - INT8：被量化元素存储约减半，质量变化不固定
  - INT4：被量化元素存储约减少 75%，总显存还含 KV、workspace、scale/metadata，质量依方案与任务
- **QAT（量化感知训练）作为候选方案，而非保证有效的兜底**
  - 核心：PTQ 不满足质量要求时，比较更高精度、其他量化/校准配置与 QAT 的成本和收益
  - 机制：在训练/微调阶段就模拟量化误差，让模型适应低精度
  - 与 PTQ 的关系
    - PTQ：训练后量化，成本低，精度有损
    - QAT：训练/微调中模拟量化误差，可能恢复质量但不保证无损；部署内核另验证
  - 工程要点
    - 保留稳定精度基线；QAT 要有训练数据、预算与兼容部署内核，并回归质量与性能
    - QAT 机制、STE 和与 QLoRA 的区别见[训练卷：量化感知训练](LLM训练知识体系.md#36-量化感知训练qat与部署衔接)
- 工程要点
  - 量化后必须评估精度损失
  - 不同任务对量化敏感度不同
  - 量化不是万能的，有些模型量化后效果崩

### 3.4 批处理与调度

- 静态批处理
  - 核心：一次处理固定数量的请求
  - 问题：请求长度不同，短请求等长请求，效率低
- Continuous Batching（连续批处理）
  - 核心：动态组批，请求完成即退出，新请求即加入
  - 优势：吞吐大幅提升，延迟可控
  - 采用者：vLLM、TensorRT-LLM、TGI
- 调度策略
  - FCFS：先到先服务，公平但可能长请求阻塞
  - 优先级：高优先级先处理
  - SJF：短作业优先，降低平均延迟
  - 公平调度：避免饥饿
- Chunked Prefill
  - 核心：长 prompt 分块 prefill，避免阻塞 decode
  - 优势与取舍：可减少长 prefill 对 decode 的阻塞、改善 ITL；chunk 大小和调度可能增加 TTFT，需按负载评估
- Speculative Decoding（投机解码）
  - 核心：用小模型草拟多个 token，大模型验证
  - 优势与取舍：受草稿成本、接受率、batch 与硬件影响，不保证固定倍数；分布保持需正确验证/拒绝采样，近似方案另作质量评测
  - 变体：Medusa、EAGLE、Lookahead
  - 适用：decode 是瓶颈的场景

### 3.5 推理优化

- 算子融合
  - 核心：把多个算子合并为一个，减少 kernel launch 开销
  - 常见：LayerNorm + Linear、Attention 融合
- CUDA Graph
  - 核心：把整个推理图捕获为静态图，减少 launch 开销
  - 适用：decode 阶段，固定 shape
- FlashAttention（推理版）
  - 核心：分块计算 + 在线 softmax，降低显存
  - 推理优势：支持长上下文
- FlashDecoding
  - 核心：decode 阶段并行化，加速长序列 decode
- 分页注意力（PagedAttention）
  - 见 3.2 KV Cache 管理
- 张量并行推理
  - 核心：模型切分到多卡，并行推理
  - 适用：单卡放不下的大模型
- 流水线并行推理
  - 核心：模型分层切分，流水线执行
  - 适用：超大模型
- 专家并行推理（MoE）
  - 核心：不同专家分布在不同卡上
  - 挑战：All-to-All 通信

### 3.6 服务化

- API 网关
  - 职责：鉴权、限流、路由、日志
  - 常见：Nginx、Kong、APISIX
- 限流
  - 核心：防止过载
  - 策略：令牌桶、漏桶、滑动窗口
- 降级
  - 核心：过载时降级服务
  - 策略：小模型替代、缓存命中、拒绝新请求
- 负载均衡
  - 核心：请求分发到多实例
  - 策略：轮询、最少连接、一致性哈希
- 多实例部署
  - 核心：多个推理实例，水平扩展
  - 挑战：模型加载、显存管理、版本一致性

### 3.7 分布式推理与架构

- 张量并行（TP）
  - 核心：层内切分，每卡算一部分
  - 通信：每层 all-reduce
  - 适用：单卡放不下的大模型
- 流水线并行（PP）
  - 核心：层间切分，不同卡算不同层
  - 通信：层间传递激活
  - 适用：超大模型
- 专家并行（EP）
  - 核心：MoE 专家分布到不同卡
  - 通信：All-to-All
  - 挑战：负载均衡、通信开销
- 混合并行
  - 核心：组合 TP + PP + EP
  - 适用：超大模型 + 多卡部署
- 多实例并行
  - 核心：多个独立实例，水平扩展
  - 适用：模型能单卡放下时
- **【定稿】PD 分离（Prefill-Decode Disaggregation）**
  - 核心问题：Prefill 和 Decode 混跑互相干扰
    - Prefill 是计算密集型，占用大量算力
    - Decode 是访存密集型，需要持续低延迟
    - 混跑时，长 prompt 的 Prefill 阻塞 Decode，导致 TPOT 抖动
  - 核心思想：把 Prefill 和 Decode 拆到不同的 GPU 集群
    - Prefill 集群：大算力卡，处理输入
    - Decode 集群：高显存带宽卡，逐 token 生成
    - 中间通过 KV Cache 传输连接
  - 代表架构
    - **Mooncake**：月之暗面的分离式架构
    - **vLLM 分离式 prefill/KV connector**：具体支持与限制按版本检查；V1 引擎不等于自动启用 PD 分离，见[官方说明](https://docs.vllm.ai/en/latest/features/disagg_prefill/)
    - **字节、阿里等大厂**：自研 PD 分离架构
  - 优势
    - Prefill 和 Decode 各自优化，互不干扰
    - 资源利用率更高，成本更低
    - 长上下文场景 TPOT 更稳定
  - 挑战
    - KV Cache 传输：网络带宽、延迟、序列化开销
    - 调度复杂度：两个集群的协调
    - 故障处理：任一集群故障都影响整体
  - 与 Chunked Prefill 的关系
    - Chunked Prefill：软件解法，把长 prefill 分块，减少阻塞
    - PD 分离：架构解法，物理隔离两个阶段
    - 两者可以组合使用

## 四、推理 vs 训练

- 本质区别
  - 训练：前向 + 反向 + 参数更新，吞吐导向
  - 推理：只做前向传播，延迟导向
- 优化目标不同
  - 训练优化：单位时间处理多少 token
  - 推理优化：单位请求多快返回 + 单位成本服务多少请求
- 硬件需求不同
  - 训练：大显存、高带宽、多卡互联
  - 推理：低延迟、高并发、成本敏感
- 技术栈不同
  - 训练：PyTorch、DeepSpeed、Megatron
  - 推理：vLLM、TensorRT-LLM、SGLang
- 选型判断
  - 训练完的模型 → 推理部署
  - 推理约束 → 反向影响训练决策（见闭环体系）

## 五、高级推理范式

- Speculative Decoding
  - 核心：小模型草拟 + 大模型验证
  - 变体：Medusa、EAGLE、Lookahead
- Multi-Token Prediction
  - 核心：一次预测多个 token
  - 代表：Medusa
- 树状解码
  - 核心：并行探索多个候选路径
  - 代表：Tree of Thoughts 推理版
- 推理时计算扩展
  - 核心：推理时增加计算量提升质量
  - 代表：o1 风格的思维链推理
  - 权衡：质量提升 vs 延迟/成本增加
- 结构化输出
  - 核心：约束输出格式（JSON、XML）
  - 方法：Grammar-based decoding、JSON mode
- 多模态推理
  - 核心：图文混合推理
  - 挑战：视觉 token 计算、模态对齐
  - **【定稿】视觉预处理一致性**
    - 核心问题：推理遵循模型发布的 processor/patch/位置规则，rollout 与 logprob 重算使用一致有效输入
    - 训练侧 resize：按训练 recipe 做 resize
    - 推理侧 resize：按发布的 processor 配置，不盲用引擎默认
    - 不一致的后果：视觉 token 错位 → logprob 偏差 → 输出异常
    - 工程要点
      - 插值方法、目标尺寸、padding 策略都要对齐
      - 绑定 processor、模型和 patch/位置规则版本；训练随机增强与标准推理预处理区分
      - 这是多模态训练卷和推理卷的跨卷接缝

## 八、成本与性能工程

- 成本构成
  - 硬件成本：GPU 采购/租用
  - 电力成本：GPU 功耗
  - 运维成本：人力、监控
  - 网络成本：带宽
- 成本优化
  - 量化：降低显存和计算量
  - 批处理：提升吞吐
  - 缓存：减少重复计算
  - 模型路由：简单请求用小模型
  - 按需扩缩容：低峰期缩容

### 8.1 容量估算与负载测试合同

**KV 与权重**

对标准 MHA/GQA/MQA、各层同配置且不考虑共享前缀，活跃 KV 存储近似为：

$$
M_{\mathrm{KV}}\approx 2BTLH_{\mathrm{KV}}d_hs_{\mathrm{KV}}.
$$

$B$ 为并发序列数，$T$ 为每序列当前缓存 token 数，$L$ 为层数，$H_{\mathrm{KV}}$ 为 KV 头数，$d_h$ 为头维度，$s_{\mathrm{KV}}$ 为每元素字节数；2 对应 K/V。长度不同时用长度之和替代 $BT$。分页、共享前缀、量化元数据、滑动窗口、MLA/混合架构需要另外计算。

权重粗估为参数数乘位宽除以 8，另计未量化层、scale/metadata。设备总内存还包括 workspace、激活、通信 buffer、碎片和安全余量；多卡划分按具体引擎测量。以这些项决定最大活跃 token、并发、排队和拒绝策略，不只按“几 B 模型”选显存。

**延迟与实验**

完成 $n_{\mathrm{out}}\ge1$ 个 token 的请求，可粗估 $T_{\mathrm{E2E}}\approx T_{\mathrm{TTFT}}+(n_{\mathrm{out}}-1)\overline{T}_{\mathrm{TPOT}}$；需说明 TTFT 的测量起点是否包含网络、排队和预处理，TPOT 是平均 inter-token latency，不掩盖尾延迟。

固定模型/引擎/硬件/精度、输入输出长度分布、到达率、并发、预热与缓存命中状态。开环到达率与闭环固定并发分开，报告 P50/P95/P99、成功 token 吞吐、超时/失败、取消释放、队列和峰值显存。保留失败请求，不只计算成功短请求。质量/安全回归与性能同时通过才上线。

见[评测方法](评测与实验方法.md)与[CPU/真实服务验收区别](实践与验收清单.md)。

## 十一、落地工程难点

- 显存瓶颈：KV Cache 占显存，限制并发
- 延迟优化：TTFT 和 TPOT 都难优化
- 成本控制：GPU 成本高，利用率难提升
- 量化精度：量化后精度损失难控制
- 批处理效率：请求长度差异大，批处理效率低
- 多实例一致性：多实例部署，版本一致性难保证
- 国产芯片适配：昇腾等生态不完善
- 长上下文推理：长上下文 KV Cache 爆炸
- MoE 推理：专家并行通信开销大
- PD 分离工程：KV Cache 传输、调度协调、故障处理 【定稿】
- 多模态推理预处理：训练和推理 resize 不一致 【定稿】
- 核心认知：推理部署是「工程密集型」，不是「算法密集型」，工程细节决定成败

### 11.1 推理部署常见反模式

- 不做容量与质量评估直接部署
  - 表现：FP16 直接部署，显存不够
  - 后果：并发低，成本高
  - 正解：按场景选择量化级别
- 量化后不评估精度
  - 表现：量化后直接上线，不测效果
  - 后果：精度崩了不知道
  - 正解：量化后回归质量与性能；PTQ 不达标时先比较更高精度、其他量化/校准配置，再评估 QAT 的收益与训练成本，不保证 QAT 无损
- 不用 Continuous Batching
  - 表现：静态批处理，短请求等长请求
  - 后果：吞吐低，延迟高
  - 正解：用 Continuous Batching
- 忽略 KV Cache 管理
  - 表现：KV Cache 不做分页、不做前缀共享
  - 后果：显存浪费，并发低
  - 正解：PagedAttention + Prefix Caching
- 可用性需求与部署方式不匹配
  - 表现：有故障容错或扩容 SLO，却仍依赖单实例且没有恢复方案
  - 后果：实例故障影响服务，可用性达不到约定
  - 正解：按 SLO 设计副本、负载均衡、故障恢复和容量；学习原型或可容忍中断的任务可以单实例部署
- 不做限流降级
  - 表现：没有限流，过载直接崩
  - 后果：雪崩
  - 正解：限流 + 降级 + 熔断
- 不监控关键指标
  - 表现：只看 QPS，不看 TTFT/TPOT
  - 后果：用户体验差不知道
  - 正解：全链路监控
- 长上下文不做优化
  - 表现：长上下文直接推理，KV Cache 爆炸
  - 后果：无法支持长上下文
  - 正解：KV Cache 量化 + 淘汰策略 + FlashDecoding
- MoE 不估容量与通信
  - 表现：只看激活参数，忽略全部专家权重
  - 后果：可能显存不足或通信成为瓶颈
  - 正解：可放下的小模型能单卡运行；多卡按硬件/负载评估 TP/EP、卸载与 All-to-All
- 忽略国产芯片适配
  - 表现：只考虑 NVIDIA，不考虑国产芯片
  - 后果：国产化要求时无法落地
  - 正解：提前评估国产芯片适配
- **【定稿】长上下文混跑不验证调度与干扰**
  - 表现：Prefill 和 Decode 混跑，长 prompt 阻塞 decode
  - 后果：TPOT 抖动，长上下文体验差
  - 正解：Chunked Prefill 或 PD 分离架构
- **【定稿】多模态推理不做视觉预处理一致性校验**
  - 表现：未按发布 processor 处理视觉输入
  - 后果：视觉 token 错位，输出异常
  - 正解：推理遵循模型发布的 processor/patch/位置规则，rollout 与 logprob 重算使用一致有效输入
