# RAG 知识地图

> 本页保留知识结构、关键结论、选型判断与验收入口，便于独立复习；推导、方案细节和实例统一维护在 [RAG 专题内容](../AI专题内容/07-RAG知识体系内容.md)。返回[总索引](00-总索引.md)。

## 一、目标与边界

RAG 用外部资料辅助回答知识依赖问题。学习重点不是记住一套固定组件，而是能判断资料是否足够、检索是否找对、答案是否被证据支持，以及更新和权限变化后是否仍然可靠。

本地图以文本知识库为主；结构化数据查询、多模态检索与真实生产服务需要分别验证。RAG 不保证消除幻觉，也不能替代模型的通用能力、事务系统或权限控制。

## 二、先修与学习顺序

先看[基础与模型原理](02-基础与模型原理.md)中的向量表示和 Transformer，再用[评测与实验方法](03-评测与实验方法.md)明确数据划分、基线与指标口径。

1. **建立最小闭环**：读资料 → 切片 → 检索 → 生成/摘录 → 引用 → 分层评测。先跑[端到端 RAG 教学案例](08-端到端RAG教学案例.md)，弄清它的离线摘录基线不等于真实 LLM。
2. **诊断质量瓶颈**：区分知识缺失、解析/切片错误、检索漏召、上下文噪声、生成错误和引用不支持；固定问题集后再逐项改动。
3. **处理工程边界**：版本、权限、删除、缓存、延迟和成本进入验收；对真实服务和模型效果保留“未验证”状态，不能用教学样本冒充生产结论。

## 三、核心知识结构

**1. 先判断是否适合用 RAG**

- 适合：答案依赖可更新、可授权、可核查的外部资料，例如产品手册、政策和内部文档。RAG 使资料与模型参数解耦，但资料更新仍需解析、索引发布与缓存失效。
- 不适合单靠 RAG：精确统计、金额计算、事务操作和强一致状态查询。它们通常需要数据库、计算程序或业务 API；检索到一段文本不等于完成了计算或操作。
- 不把“有引用”当成“正确”：检索可能命中旧版本、无权限或不相关资料，生成也可能曲解资料。问题、证据、结论和引用要分别检查。

**2. 从资料到可检索证据**

| 环节 | 核心判断 | 常见错误 |
| --- | --- | --- |
| 接入与解析 | 记录来源、版本、时间、授权；检查 PDF/OCR、表格和代码是否被正确解析 | 原文已缺失或行列关系被破坏，后续检索无法补救 |
| 切片 | 根据段落、标题、表格等结构选边界；比较不同粒度与重叠 | 太小丢上下文，太大引入噪声；固定 token 数不是通用最优值 |
| 索引 | 保留原文、稳定 ID、元数据与适用的词项/向量索引 | 只存向量不存出处；新旧模型或不同编码配置的向量混用 |
| 发布 | 新索引验证后切换，删除和权限撤销同步处理旧索引与缓存 | 新版片段与旧版答案混用，回滚时复活已撤销资料 |

向量检索的 Query 与 Document 编码必须属于配套、兼容的向量空间；可以是参数不同的两个 tower，不要求“同一个模型”。纯 BM25 基线不需要向量数据库。Embedding、索引类型和切片大小都应与问题集一起评估，而不是先按工具名选型。

**3. 从问题到候选证据**

- 多轮对话先判断当前问句是否缺少实体、时间或约束；必要时把对话改写成独立检索问题，但保留原问题与改写结果，以便排查改写引入的错误。
- BM25 等稀疏检索利用词项匹配，适合型号、编号和专有词；稠密检索利用向量相似度，适合词面不同但语义接近的表达。两者都有盲区，不能预设哪种总是更好。
- 混合检索是把不同检索器的候选融合；多 Query 或多来源召回是另一维度。增加一路召回前，先证明简单基线在目标问题上漏召，并记录新增延迟与成本。
- Rerank 只能在已召回候选中调整顺序，不能找回第一阶段完全漏掉的证据。先看 Hit@K/Recall@K，再讨论排序质量与送入模型的上下文。
- 数值、日期、租户和权限等硬条件不能只靠向量相似度。可用结构化过滤、数据库查询或可验证计算；无权限内容不得进入生成上下文、返回结果或非授权缓存。
- Top-K 是实验参数：太小会漏掉多证据答案，太大可能增加噪声与延迟。按问题类型、证据覆盖和上下文预算选择，并保留固定基线做对照。

**4. 从证据到答案**

- 上下文组装要保留片段来源、文档版本和授权信息，去除重复片段；父子切片或邻域扩展可补全语境，但也可能把无关内容带入。
- Prompt 约束模型根据资料作答，不能替代后端的权限控制与引用校验。检索片段是不可信输入，其中的“忽略规则”等文字属于数据，不能当系统指令执行。
- 区分三个问题：答案是否**事实正确**、是否**忠实于提供的资料**、引用是否**真的支持对应结论**。忠实于错误资料的回答仍可能事实错误；有来源编号也可能是假引用。
- 对无资料、证据冲突或证据不足的知识依赖问题，应按风险选择拒答、继续检索或转人工；不能只删除引用而继续返回原结论。

**5. 分层评估与诊断**

| 层次 | 最少要看什么 | 不要误读为 |
| --- | --- | --- |
| 检索 | Hit@K 是否至少命中一个相关项；Recall@K 是否覆盖所需证据；MRR/nDCG 是否排得靠前 | 命中一条就足以回答多证据问题 |
| 上下文 | 相关片段是否进入最终 Prompt，是否混入旧版、重复或无权限内容 | 检索候选合格就代表上下文合格 |
| 生成 | 答案正确性、忠实度、无答案处理及数值/时间条件 | LLM Judge 分数等于事实真值 |
| 引用 | 每条需溯源结论是否有引用、引用原文是否支持该结论 | 标注了文档编号就完成了校验 |
| 服务 | P95/P99 延迟、失败率、每个成功任务成本、更新与撤销传播 | 一次 Demo 成功就可以投入生产 |

先固定数据快照、问题集、权限条件和简单基线；开发集用于迭代，最终留出集不反复调参。无命中、无答案、超时和拒答单列，不能从分母中悄悄删掉。指标口径与报告模板见[评测方法](03-评测与实验方法.md)。

**6. 运行与持续更新**

- 文档变更可能改变切片边界，不能仅凭文件名判断哪些 chunk 仍有效；稳定来源 ID、版本和删除策略比“增量写入成功”更重要。
- 权限撤销、强制删除要传播到索引、缓存、副本和日志治理；它们不应被旧快照回滚重新暴露。
- 监控按解析、索引、检索、重排、生成、引用校验分别记录时延、失败与版本，才能定位问题；线上点击或点踩不能直接代替有标注的检索评测。
- 优化顺序由瓶颈决定：若证据不存在，先补数据；若有资料但没召到，先改解析/切片/检索；若召到却答错，再看上下文与生成；若答案对但引用错，修引用对齐。

**7. 特殊语料与扩展策略**

| 场景 | 可考虑的方法 | 先验证什么 |
| --- | --- | --- |
| 长文档片段失去语境 | 父子切片、句子窗口、Contextual Retrieval、Late Chunking | 相比简单结构切片是否减少漏召；额外索引与生成成本是否值得 |
| 表格、表单或精确数值 | 保留行列结构、字段索引、数据库/计算组件 | 条件解析、数值比较和引用是否准确 |
| 冷启动或知识库稀疏 | 明确覆盖范围、优先补关键文档、无依据时拒答/转人工 | 未覆盖问题是否被误答为已有知识 |
| 多轮省略与指代 | 结合历史改写 Query，保留原问句与关键实体 | 改写是否加入用户没说的实体或约束 |
| 多源知识 | 授权路由、源端检索、候选去重与融合 | 不同源的 ACL、版本、分数尺度与超时处理 |
| 跨文档复杂问题 | 子问题分解、迭代检索或 GraphRAG 等 | 简单多路检索是否已经满足证据覆盖，复杂方法是否带来可测收益 |

这些是候选方案，不是必须依次升级的阶梯。尤其是联邦检索只表示查询时跨源分发/融合，不自动等于数据不离源；返回片段、日志和缓存仍需审计。更复杂的自适应或 Agentic RAG 还要限制检索轮数、成本及失败终止条件。

**8. 成本、部署与反馈闭环**

- 成本不只有生成 token：解析与建索引、embedding、存储、检索、重排、引用校验、失败重试都要计入。比较方案时固定质量门禁，报告每个成功任务的总成本。
- 时延拆成检索、重排、上下文组装、模型首 token、生成及校验；不能只测单次顺序请求。固定负载下看 P95/P99、超时、限流和降级。
- 灰度发布要绑定语料快照、切片/索引版本、embedding 配置、Prompt 与模型版本。可回滚内容发布，但权限撤销或强制删除不能随旧快照一起恢复。
- 线上负反馈是待分析线索，不是自动训练标签。先脱敏、归因并加入开发/回归集；最终留出集继续隔离，避免反复优化造成虚假进步。

## 四、常见决策与易错点

| 情况 | 优先判断 | 不宜直接做的事 |
| --- | --- | --- |
| 资料频繁变化 | RAG 或结构化查询能否保持版本、授权和来源 | 为每次资料更新重新微调模型 |
| 输出行为或格式不稳定 | Prompt、结构化约束与微调分别能改善什么 | 把 RAG 当成改变模型行为的唯一手段 |
| 查询含精确时间或金额 | 能否解析条件并交给过滤/计算组件验证 | 只凭语义相似度返回“看起来接近”的段落 |
| 检索漏召 | 先看原文、解析、切片、词项/向量召回和 Query 改写 | 直接增加 Rerank、Agent 或更大模型 |
| 候选已包含答案但输出错误 | 看上下文组装、Prompt、证据冲突和生成错误 | 只调高 Top-K，扩大噪声 |
| 多知识源或复杂问题 | 简单集中/多源基线是否不足，是否需要路由、迭代检索 | 默认引入 GraphRAG、联邦检索或多 Agent |

RAG 与微调不是非此即彼：前者侧重提供外部依据，后者可调整模型行为或任务能力；组合前仍需做单方案基线和消融。复杂范式的前提是已定位简单方案的失败点，而不是因为术语更先进。完整原理与方法适用条件见[内容篇](../AI专题内容/07-RAG知识体系内容.md)。

## 六、动手验收

按[实践与验收清单](13-实践与验收清单.md)做一个有版本和权限标签的小型知识库，并保留以下证据：

1. 固定问题集、文档快照、gold 依据与简单检索基线；开发集和最终留出集分开。
2. 输出每题的候选片段、最终上下文、回答及引用；检索漏召和“召到却答错”分开归因。
3. 对切片、混合检索和重排逐项比较质量、延迟与成本，不预设复杂方案一定更好。
4. 测无答案、错误版本、无权限、更新、删除及缓存失效；引用必须真正支持对应结论。
5. 报告模型/索引/数据/代码版本、失败样本和未验证项；真实模型与服务未运行时不得写成已通过。

入门可先用[最小验收示例](10-最小验收示例.md)理解引用门禁，再跑[端到端案例](08-端到端RAG教学案例.md)观察文件处理与检索。两者均是教学证据，不代表生产效果。
