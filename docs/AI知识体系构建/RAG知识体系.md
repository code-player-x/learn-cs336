# RAG 完整知识体系

## 一、RAG 基础认知

- 核心定义
  - 全称：检索增强生成（Retrieval-Augmented Generation）
  - 核心解决：LLM「知识冻结」问题（训练后知识固化）
  - 本质：给LLM开「开卷考试」，生成前先检索外部知识库
- 解决的三大核心问题
  - 知识时效性：覆盖训练截止后的新信息
  - 私有知识覆盖：接入企业内部文档、产品手册等私有数据
  - 幻觉缓解：给LLM真实参考依据，降低凭空编造概率
- 核心价值
  - 知识热更新：新增文档即可生效，无需重训模型
  - 答案可溯源：每条回答可追溯到原始文档片段
  - 知识与模型解耦：更新知识无需修改模型参数

## 二、RAG 完整工作流程

- 离线阶段（建库，一次性完成）
  - 文档加载：支持PDF/Word/网页等多格式
  - 文档切割（Chunking）：切成500~1000token片段，保留重叠避免语义截断
  - 向量化：用Embedding模型将文本转为高维向量
  - 入库：向量+原文+元数据存入向量数据库
- 在线阶段（每次提问实时执行）
  - Query改写：将口语化问题优化为适合检索的形式
  - 向量粗排：查询向量化后召回Top-K相关chunk
  - Rerank精排：Cross-Encoder模型对候选结果重排序，保留Top3~5
  - Prompt拼接：问题+精排片段组装prompt，约束模型基于资料回答
  - LLM生成：基于参考资料输出答案，附带来源溯源
- 关键认知
  - 粗排：速度快但精度低，负责快速缩小范围
  - 精排：精度高但速度慢，仅对粗排少量候选做深度判断
  - Embedding模型必须与建库时完全一致

### 2.1 多轮对话场景下的 RAG 流程

- 核心问题：单轮独立 Query 设计在真实业务中不成立，90% 以上是多轮对话
  - 用户上一句问“产品A怎么退款”，下一句说“那它的运费呢”
  - 当前句本身信息不完整，必须融合对话上下文才能正确检索
- 对话历史指代消解
  - 把“它”“这个”“那款”还原为具体实体（如“产品A”）
  - 指代消解失败 → Query 改写错误 → 检索全盘失效
- Query 改写融合对话上下文（Condense Question）
  - 不只看当前这一句，而是把对话历史压缩成一个独立完整的检索 Query
  - 常见做法：用 LLM 把多轮对话凝练为单轮标准问句
- 对话记忆管理
  - 滑动窗口：只保留最近 N 轮，简单但可能丢失早期关键信息
  - 摘要压缩：对历史对话做摘要，保留语义但降低 token 占用
  - 关键实体抽取：把对话中出现的实体、约束、偏好结构化存储
- 多轮场景下的检索策略
  - 是否每轮都检索：简单追问可复用上轮结果，新话题必须重新检索
  - 检索结果复用：上轮已召回的 chunk 在本轮仍相关时，避免重复检索
  - 多轮累积上下文：把多轮信息合并后统一构造 Prompt，而非每轮孤立拼接
- 工程门槛认知
  - 多轮对话是 RAG 从 Demo 到真实业务的最大门槛之一
  - 单轮 Demo 跑通只需 1~2 天，多轮场景调好需要数周

## 三、核心组件详解

### 3.1 文档切割（Chunking）策略

- Chunk存储三要素

  - 向量：用于相似度检索的「索引卡」
  - 原文：检索命中后给LLM阅读的「书页」
  - Metadata：来源、页码、章节等「书签」

- 切割粒度权衡

  - Chunk过大：语义笼统，检索精度下降
  - Chunk过小：语义不完整，上下文丢失
  - 推荐起点：500~1000token

- 主流切割策略

  - 固定大小+重叠：基础兜底，适合无结构纯文本
  - 语义边界切割：按段落/句子自然断点切割
  - 标题层级切割：针对Markdown/HTML按章节切
  - 特殊内容处理：代码按函数/类切，表格整块保留
  - 父子切割：小块检索、大块返回，兼顾精度与上下文
  - Late Chunking：先对全文编码再切分，保留跨块语义

- 切割演进方向

  - 1.0物理切割→2.0智能分块→3.0知识提取→4.0动态组装

  经典 RAG 是“检索到什么 chunk，就返回什么 chunk”。
  动态组装是“检索到什么位置，就在那个位置周围临时拼出最合适的上下文”。

- 语义截断规避

  - 切分阶段：重叠切割、语义边界切割
  - 检索阶段：句子窗口检索、父子切割、Contextual Retrieval

- 预结构化语料的特殊策略：ThemePath-RAG

  - 适用场景：法律、医学、宗教研究等知识本身已由专家构建明确「主题路径」的专业领域
  - 核心问题：传统扁平化 RAG 无法利用专家预设的先验结构，容易检索到冗余或无关证据
  - 核心思想：查询感知的证据剪枝
    - 检索前先沿专家预设的主题路径导航
    - 只从最相关的路径节点中提取证据，而非全局搜索
  - 与 GraphRAG 的区别：GraphRAG 是自动构建实体关系图，ThemePath-RAG 是利用人工/专家已有的结构化主题体系

- 结构化内容处理（表格/字段/表单）

  - 核心问题：企业文档中 30% 以上是表格、字段、结构化数据，纯文本切分效果极差
    - 表格被切断后行列对不上，语义完全丢失
    - 结构化字段（如合同金额、日期、编号）混在文本中难以精确检索
  - 表格处理策略
    - 表格转 Markdown / HTML 存储，保留行列结构
    - 表格整块保留，不参与普通文本切割
    - 复杂表格可转为结构化描述文本（如“第2行第3列为……”）
  - 结构化字段单独建索引
    - 数值、日期、枚举类字段单独建结构化索引，支持精确过滤
    - 与向量检索融合：先用结构化条件过滤，再做语义检索
  - 文本检索与结构化检索融合
    - Text-to-SQL：把自然语言问题转为 SQL 查询结构化数据
    - 混合路由：根据 Query 类型决定走向量检索还是结构化查询
  - 这是处理企业知识库的核心痛点，也是纯文本 RAG 方案最容易翻车的地方

- 时间/数值类精确查询处理
  - 问题本质：纯向量检索对精确时间/数值条件不敏感
    - “2026年Q3”和“2025年Q3”在向量空间里高度相似，容易召回错误年份
    - “超过7天”和“超过30天”语义相近，阈值条件被忽略
    - 后果：召回了语义相关但条件错误的文档，比不召回更危险
  - 正确流程：检索前先做条件解析，再走语义召回
    - 第一步：Query 解析，抽出时间/数值条件（2026 Q3、>7天）
    - 第二步：结构化过滤，用解析出的条件做 metadata pre-filter
    - 第三步：语义召回，在过滤后的子集里做向量检索
  - 实现要点
    - Query 解析可用规则+LLM混合：规则处理标准格式，LLM处理口语化表述
    - 时间条件要处理相对表述：“上个月”“最近一周”“Q3”
    - 数值条件要处理比较符：“超过”“低于”“等于”“介于”
    - 过滤条件必须前置，和权限过滤同理
  - 与 BM25 的关系
    - BM25 能匹配“2026”这个 token，但无法理解“Q3”的范围语义
    - 纯 BM25 也无法处理“超过7天”这种阈值判断
    - 所以时间/数值条件不能靠检索层解决，必须在检索前解析
  - 典型翻车场景
    - 用户问“2026年Q3营收”，召回了2025年Q3的文档，模型照答
    - 用户问“超过7天退款”，召回了“7天内退款”的文档，条件反了

### 3.2 Embedding 技术体系

- 核心本质：语义压缩，将文本映射为固定长度高维向量

- 三代算法演进

  - 第一代：静态词向量（Word2Vec/GloVe），无法处理多义词
  - 第二代：上下文向量（BERT），检索速度极慢
  - 第三代：句子级对比学习（BGE/Qwen3-Embedding），RAG标配

- 选型维度

  - 语言：中文选bge/Qwen3-Embedding，中英混合选bge-m3
  - 合规：数据不出境选开源本地部署模型
  - 评估：用业务测试集测Hit@K，比公开排行榜更贴合实际

  **Hit@K = 前 K 个检索结果里，有没有正确答案。**
  它是检索质量的第一道门槛指标，K 通常取 5、10、20。
  用自己业务的测试集测，比看公开排行榜更能反映实际效果。

- MRL套娃表示学习

  - 核心：核心语义压缩到向量前N维，支持灵活截断降维
  - 优势：低维粗筛+高维精排，大幅降低内存占用

### 3.3 向量数据库

- 核心定位：专门优化高维向量近似最近邻搜索（ANN）
- 核心索引算法
  - HNSW：精度高、速度快、内存占用大
  - IVF：内存省、适合超大规模场景
- 主流方案选型
  - Chroma：零配置上手快，适合快速原型
  - Qdrant：Rust高性能，适合中小到亿级生产
  - Milvus：分布式架构，适合千万到亿级超大规模
  - pgvector：PostgreSQL插件，适合已有业务库场景
- 关键工程能力
  - Metadata过滤、实时增量更新、混合检索
- 生产优化
  - 开启SQ8标量量化，内存占用降至1/4，召回基本无损
  - 批量写入错峰，避免Segment合并抖动

### 3.4 检索核心技术

- BM25关键词检索
  - 原理：倒排索引+词频+逆文档频率打分
  - 优势：精确词汇（型号、专有名词、数字）命中率极高
  - 劣势：无法处理同义词，词不重叠就召不到
- SPLADE 学习稀疏检索
  - 原理：用 BERT 学习“词项重要性 + 语义扩展”，输出稀疏向量，仍可用倒排索引高效检索
  - 优势：兼顾 BM25 的精确匹配和向量检索的语义扩展，能处理“同义词但词不重叠”的问题
  - 劣势：依赖模型训练质量；极冷门专有名词（如独特序列号）可能不如纯 BM25
- 向量语义检索
  - 原理：高维向量余弦相似度匹配
  - 优势：理解同义词、不同表达的语义等价
  - 劣势：对精确专有名词不敏感，容易漏召
- 混合检索（工业界标配）
  - 并行召回两路结果，用RRF互倒排名融合
  - 注：SPLADE 常可直接替代 BM25 作为稀疏侧检索器
- 多路召回
  - 额外加多路Query扩展，从不同角度改写问题检索
- Rerank精排
  - Cross-Encoder对粗排Top20候选深度打分，保留Top3~5送入LLM
  - 常见模型：BGE Reranker、Cohere Rerank、Jina Reranker
- 检索结果的去重与多样性控制
  - 核心问题：多个 Chunk 来自同一文档相邻位置，内容高度重复，塞进 Prompt 是浪费
  - MMR（最大边际相关性）
    - 在“与 Query 的相关性”和“结果之间的多样性”之间做权衡
    - 避免 Top-K 被同一文档的相似片段霸占
  - 同一文档多 Chunk 命中的处理策略
    - 合并：相邻 Chunk 合并为一个更大片段送入 LLM
    - 选最优：只保留得分最高的那个 Chunk
    - 都保留但去重：按语义相似度去重后保留
  - 工程价值：提升 Prompt 有效信息密度，降低 token 浪费

### 3.5 Query 优化

- 核心目的：弥合用户口语提问与知识库书面表述的语义鸿沟
- 四种主流方法
  - 直接改写：口语转正式句，补全指代
  - HyDE：先生成假设答案，用答案向量检索
  - Step-back：将具体问题抽象为通用背景问题
  - 多Query扩展：改写为3~5个不同角度版本分别检索
- 动态 Top-K 调整
  - 核心：不固定召回 Top3~5，根据 Query 类型动态决定召回数量
  - 事实性精确问题：取 3 条足够，多了反而引入噪声
  - 综述/对比类问题：需要 8~10 条才能覆盖全面
  - 闲聊/不需要知识的问题：0 条，直接走 LLM，不检索
  - 实现方式：Query 分类器 → 按类别映射到不同的 Top-K 值
  - 价值：同时优化效果和成本，是平衡两者的关键手段

### 3.6 Rerank 精排

- 为什么需要 Rerank
  - 向量粗排精度有限，Top-K 中常混入不相关结果
  - Cross-Encoder 能对 query 和 doc 做深度交互打分
- 常见模型
  - BGE Reranker
  - Cohere Rerank
  - Jina Reranker
- 两阶段检索
  - 粗排：向量/BM25 快速缩小范围
  - 精排：Cross-Encoder 深度判断，保留 Top3~5
- 工程注意
  - Rerank 延迟与候选数量成正比
  - 候选数一般 20~100，太多会拖慢响应

### 3.7 生成与 Prompt

- Prompt 构造
  - 系统提示：角色、约束、拒答策略
  - 上下文拼接：精排片段 + 来源编号
  - 用户问题
  - 引用要求：每条结论标注来源
- LLM 选择
  - 闭源：GPT、Claude、Gemini
  - 开源：Qwen、Llama、DeepSeek
  - 本地部署：合规场景
- 生成参数
  - temperature
  - top_p
  - max_tokens
- 上下文工程
  - Lost in the Middle：关键信息放首尾
  - 上下文窗口管理
  - 上下文压缩
  - 关键信息前置
  - 拒答策略：无资料时明确说不知道

## 四、RAG vs 微调

- 本质区别
  - 微调：将知识写入模型参数，烧进模型内部
  - RAG：不动模型参数，推理时实时检索注入知识
- 微调优劣势
  - 优势：输出风格/格式深度定制，推理无额外检索步骤，延迟低
  - 劣势：成本高，知识更新慢（需重训），答案不可溯源
- RAG优劣势
  - 优势：知识更新成本极低，答案可溯源，落地门槛低
  - 劣势：增加检索步骤导致延迟上升，效果上限被检索质量卡住
- 工程组合最佳实践
  - 微调解决「怎么说」：定制输出风格、行业术语、回答语气
  - RAG解决「说什么」：提供实时、动态的具体知识内容
  - 选型：动态知识库选RAG，深度风格定制选微调，复杂生产系统两者结合

## 五、高级 RAG 范式

- Self-RAG：生成时自动判断是否需要检索、结果是否可信
- CRAG（纠错RAG）：知识库结果差时自动降级网络搜索兜底
- GraphRAG：预构建实体关系知识图谱，支持跨文档多跳推理
- Agentic RAG：LLM自主决策多轮检索，直到信息充分再生成
- 自适应检索（Adaptive Retrieval）
  - 核心：并非所有问题都走完整 RAG 流水线
  - 简单事实查询 → 直接向量检索
  - 复杂多跳问题 → 启动 Agent 循环或图遍历
  - 价值：动态路由，平衡效果与延迟
- OmniRAG（动态检索路由）
  - 核心：不固定使用一种检索方式，根据用户意图实时判断
  - 动态选择向量搜索 / 数据库精确查询 / 知识图谱遍历中的一种或多种组合
  - 示例：查询“Python Flask 库的依赖项”适合图查询；“有哪些类似的库”适合向量检索
  - 价值：最大化利用不同检索器的优势
- 多模态 RAG
  - 图文混合检索
  - 表格问答
  - OCR + 版面理解
  - 多模态 Embedding（CLIP、BGE-VL 等）
  - 图表转文本/结构化描述
  - 视频/音频转写后检索
  - 独特挑战：跨模态对齐、融合与推理
  - 系统化问题：图文混合 PDF 统一索引、表格问答、图文检索忠实度评估
  - 所需技术：多模态嵌入模型、布局理解、专门评估基准

### 5.1 联邦 RAG（Federated RAG）

- 核心场景：知识散落在多个独立系统，无法或不应集中到统一向量库
  - 典型系统：Confluence、SharePoint、内部 Wiki、工单系统、代码仓库、CRM
  - 各系统有独立的权限体系、检索接口、数据格式
  - 合规要求数据不能离开原系统，或集中治理成本过高
- 与单库 RAG 的本质区别
  - 单库 RAG：所有知识先入库到统一向量库，查询时只查一个库
  - 联邦 RAG：知识不入库，查询时跨源实时检索，在联邦层做结果融合
- 核心架构
  - 查询分发层：把一个用户 Query 分发到多个知识源
  - 各源独立检索：每个源用自己的检索方式（向量/BM25/API）
  - 结果融合层：统一打分、去重、排序，跨源结果合并
  - 权限统一层：各源权限体系不同，在联邦层统一做权限过滤
  - 生成层：融合后的结果送入 LLM 生成带引用的答案
- 核心技术挑战
  - 跨源结果打分不可比：不同源的相似度分数尺度不同，不能直接比较
  - 跨源去重：同一文档在多个源都有，需要识别并去重
  - 跨源权限统一：各源权限模型不同，联邦层如何统一表达和执行
  - 单源不可用降级：某个源超时或故障时，如何降级而不影响整体
  - 延迟叠加：并行请求多个源，整体延迟取决于最慢的源
- 学术进展（2024-2025 加速）
  - 隐私保护型：C-FedRAG 在可信执行环境中运行检索和生成，确保原始数据不离开本地；FRAG 通过同态加密实现加密向量搜索
  - 效率优化型：RAGRoute 学习将查询路由到高价值数据源，减少 75% 的冗余流量；HyFedRAG 通过三层缓存将推理延迟降低最多 80%
  - 个性化适配型：pFedRAG 专注于联邦环境下 embedding 模型的个性化调优，Recall@k 提升高达 76%
  - 表示级集成型：FedRepRAG 不做原始文本传输，而是传输“表示级”的嵌入 token，检索上下文长度减少 19-398 倍
  - 综述结论：联邦 RAG 研究已从“算法概念验证”（2020-2022）进入“整体架构”阶段（2023-2025），但部署研究仍然稀少，多数是实验室环境
- 工业进展
  - SWIRL AI Enterprise：目前最接近“联邦 RAG 产品化”的商业方案，定位“Federated AI Search”
    - 连接 100+ 企业系统（SharePoint、Salesforce、ServiceNow、Confluence 等）
    - 数据不移动、不重新索引，查询时跨源实时检索
    - AI 重排序后生成带引用的答案，支持 Grounded RAG
    - 严格来说是“联邦搜索 + RAG 生成”的混合体，非完整联邦训练架构
  - 阿里云百炼（2026.07）：推出“多库混合检索问答”，支持 15 个知识库联合检索
    - 用户可按业务重要性设置权重
    - Agent 自动拆解问题、多轮检索、切换工具
    - 虽非严格“联邦”（数据仍在阿里云体系内），但说明跨多知识库混合检索正成为企业级 RAG 标配能力
- 成熟度判断
  - 学术上已有完整框架和基准测试
  - 工业界有可部署的商业产品
  - 但大规模落地案例还不多，离“开箱即用”有距离
  - 适合场景：知识散落多系统、数据不能集中治理、合规要求数据不出原系统
  - 不适合场景：企业统一知识库（集中式单库 RAG 更简单高效）
- 与现有体系的关系
  - 本体系默认“所有知识先入库到统一向量库”
  - 联邦 RAG 是“知识不入库，查询时跨源实时检索”的独立架构范式
  - 两者不是替代关系，而是面向不同场景的互补方案
- 工程复杂度预警
  - 联邦 RAG 的工程复杂度显著高于单库 RAG
  - 成熟方案少，多数需要自研联邦层
  - 延迟、权限、去重、降级每一个都是独立难题
  - 建议：除非确实需要跨源实时检索，否则优先考虑集中式单库 RAG

## 六、幻觉防控体系

- 幻觉来源
  - 检索层：未召回到内容，LLM凭空编造
  - 生成层：检索到内容但LLM过度发挥
- 分层防控
  - 基础必做：Prompt强约束，无资料则明确拒答
  - 质量门控：Rerank分数低于阈值直接拒答
  - 事后校验：生成后核查每条信息是否有原文依据
  - 强制溯源：结构化输出每条结论的来源编号
- 核心原则：治幻觉先治检索，检索质量是幻觉最大来源

### 6.1 引用对齐校验（Citation Alignment）

- 核心问题：模型标了来源编号，不代表引用真的对齐
  - 模型标了 [1]，但 [1] 对应的原文其实不支持这句话
  - 模型把多个来源的信息混在一起，只标了单一来源
  - 模型编了一个不存在的来源编号
- 为什么比“不标来源”更危险
  - 不标来源：用户知道不可信
  - 标了错来源：用户以为可溯源，给了虚假的安全感
- 校验方法
  - 生成后逐条核查：每条带引用的结论，其引用原文是否真的支持该结论
  - 可用 NLI（自然语言推理）模型判断“原文 → 结论”是否 entail
  - 不支持的引用标记为“引用不一致”，触发重生成或降级为无引用回答
- 工程注意
  - 引用对齐校验是生成后处理，增加延迟但显著提升可信度
  - 高合规场景（金融、医疗、法律）应作为必做项

## 七、RAG 效果评估

- 检索层评估
  - Hit@K：相关内容是否被召回
  - MRR：正确内容的排名位置，指导Rerank优化
  - Recall / Precision / NDCG
- 生成层评估（RAGAs框架）
  - Faithfulness（忠实度）：答案内容是否全部来自检索资料
  - Answer Relevancy（答案相关性）：答案是否真正回答用户问题
  - Context Recall（上下文召回率）：回答所需信息是否被覆盖
  - Context Precision（上下文精确率）：相关内容是否排在前面
- 评估方法
  - 人工评估
  - 自动评估：RAGAS、TruLens、DeepEval
  - LLM as Judge
- 评估数据集
  - 构建问答对
  - 标注相关性
  - 难例挖掘
- 线上核心指标
  - 负反馈踩率、追问率、转人工率、会话解决率
- Bad Case 分层归因
  - 检索问题：没召到 / 召到不相关
  - 生成问题：有资料但答错 / 幻觉
  - 数据问题：文档缺失 / 解析错误
- Topics vs. Capabilities 诊断框架
  - Topics（内容覆盖度）问题：知识库本身缺少回答所需的信息
  - Capabilities（处理能力）问题：知识库有信息，但系统无法有效处理
    - 无法理解时间表述（“上周的变化”）
    - 无法进行数值计算（“统计文档中的项目数”）
    - 无法进行实体消歧（“指的是哪个‘苹果’”）
  - 价值：帮助工程团队精准决定是“补充文档”还是“升级检索/生成组件”
- 引用对齐评估
  - 引用支持率：带引用的结论中，引用原文真正支持结论的比例
  - 引用覆盖率：需要溯源的结论中，实际标注了来源的比例
  - 两个指标分开看：支持率低 = 引用错；覆盖率低 = 漏标引用

## 八、知识库动态更新

- 核心挑战：文档变更会导致切割边界变化，无法直接局部更新
- 基础流程
  - 变更感知：文档hash检测内容变化
  - 更新策略：先删除该文档所有旧Chunk，再重新切割入库
- 生产级优化
  - 灰度更新：新旧版本并行，验证后切流量，支持秒级回滚
  - 细粒度更新：diff算法仅更新变更章节的Chunk
  - 增量索引：新数据写入独立索引，避免线上抖动

### 8.1 冷启动与知识库稀疏场景

- 核心问题：体系默认知识库已建好，但真实项目第一阶段往往是空库或只有少量文档
  - 空库/稀疏库时检索必然召回差，硬检索只会召到噪声
  - 新领域文档少，Embedding 模型在该领域表现差
- 冷启动期典型困境
  - 先攒文档还是先调检索：没有足够文档，检索调优无从谈起
  - 用户已经来问了，但知识库还没准备好
- 降级策略
  - 空库/稀疏库时，走通用 LLM 回答 + 明确告知“暂无相关资料”
  - 不要硬检索：召回差时强行拼接噪声上下文，比不检索更容易产生幻觉
  - 设置召回质量阈值：Rerank 分数或召回数量低于阈值时，走降级路径
- 冷启动期的知识库建设
  - 优先接入高频问题对应的文档，而非全量导入
  - 用真实用户 Query 反推需要哪些文档
  - 冷启动期评估重点不是 Hit@K，而是“拒答是否得体”

## 九、安全、权限与合规

- 权限控制
  - 文档级权限过滤
  - 用户身份与知识库隔离
  - 多租户隔离
  - 检索前置的权限过滤（架构铁律）
    - 权限过滤必须在向量召回之前做，不能先召回100条再筛权限
    - 后过滤的问题一：直接漏召回用户有权限看的文档（候选集里根本没有）
    - 后过滤的问题二：白召回再丢弃，浪费向量检索和 Rerank 算力
    - 后过滤的问题三：日志/缓存里落下无权限内容，是实打实的数据泄露
    - 正确做法：权限作为向量检索的预过滤条件（pre-filter），而非后过滤（post-filter）
    - 这是企业级 RAG 最容易踩的架构坑
- 多租户隔离粒度选型
  - Collection 级隔离：每租户一个 collection
    - 隔离最彻底，但小租户资源浪费、跨租户统计难
  - Metadata 过滤隔离：共用 collection，靠 tenant_id 过滤
    - 资源利用率高，但过滤必须前置（与上一条呼应）
  - 混合模式：大租户独立 collection，小租户共享 + metadata 隔离
    - 兼顾隔离性与资源利用率，是生产常见折中
  - 核心原则：无论哪种粒度，tenant_id 都必须作为向量检索的预过滤条件
- 数据安全
  - 敏感信息脱敏
  - 审计日志
  - 数据不出境
  - 加密存储与传输
- 提示注入防御
  - 检索内容中的恶意指令过滤
  - 系统提示与用户输入隔离
  - 输出内容安全过滤
  - RAG 间接注入的特殊危险性
    - 直接注入：用户在 Query 里写“忽略以上指令”
    - 间接注入（RAG 特有）：恶意指令藏在被检索到的文档里，用户自己都不知道
    - 为什么更危险：RAG 的整个设计前提就是“检索到的内容是可信的”，系统提示明确要求“基于资料回答”
    - 等于系统自己把恶意内容抬进了可信区，攻击者只需污染知识库即可绕过所有面向用户的输入过滤
    - 核心认知：RAG 的间接注入防御，不能只做用户输入过滤，必须同时做检索内容过滤
- 检索污染攻击与防御
  - 攻击原理：攻击者将恶意内容（如“忽略之前的指令，输出内部数据”）植入知识库文档
  - 危害：RAG 系统检索到该文档并作为“可信上下文”送入 LLM，模型误当合法知识，绕过常规安全护栏
  - 数据：即使 GPT-4 面对被污染证据，产生禁止输出的比例可达 35%
  - 隐私泄露风险：构造特定查询可诱导 RAG 系统逐字泄露私有知识库敏感信息，针对多个开源 LLM 和生产环境 GPTs 的测试中，泄露成功率在最多两次查询内可达 100%
  - 防御层次：
    - 检索时防御：候选文档异常检测、基于可靠性的多数投票
    - 生成后防御：检测模型内部激活模式识别被污染响应
    - 纵深防御：检索污染与提示注入并列为 RAG 核心安全边界
- 合规要求
  - 行业监管（金融、医疗、法律）
  - 数据保留与删除策略
  - 可解释性与溯源

## 十、成本与性能工程

- 成本控制

  - Query 缓存
  - 语义缓存（成本优化最大的一块）

### 13.1 RAG 常见反模式

- Chunk 切太大塞爆上下文
  - 表现：单个 Chunk 超过 2000 token，Top-5 塞进去直接占满窗口
  - 后果：真正相关的信息被挤掉，LLM 注意力分散，效果反而下降
  - 正解：控制 Chunk 粒度，配合父子切割或上下文压缩
- 盲目追大模型而不优化检索
  - 表现：效果不好第一反应是换更大的 LLM
  - 后果：成本翻倍但效果提升有限，因为问题出在检索层没召到
  - 正解：治幻觉先治检索，检索质量是效果的最大来源
- 离线测试集和线上真实用户分布不一致
  - 表现：离线评估指标很好，上线后用户反馈很差
  - 后果：优化方向跑偏，做了大量无效调优
  - 正解：测试集要从真实用户 Query 中采样，定期更新
- 把 Rerank 当万能药不做召回优化
  - 表现：指望 Rerank 把不相关的结果排掉
  - 后果：Rerank 只能重排，不能召回没召到的内容，召回层漏了就是漏了
  - 正解：先保证召回率，再用 Rerank 提精度
- 元数据过滤漏配导致召回一堆无效文档
  - 表现：没有按部门、版本、生效日期做过滤
  - 后果：召回了过期文档、无权限文档、无关部门文档
  - 正解：元数据过滤和权限过滤一样，必须在召回前置
